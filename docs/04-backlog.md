## 1. 港股支持（2026-09-29 记录）

**背景**：用户持有港股，看板目前只有 A 股。

### 为什么当初没做

1. **P0 需求清单就是 A 股**，没有港股条目；
2. **一半功能在港股没有对应概念**（见下表）；
3. **代码里写死了 A 股假设**，填 5 位港股代码不是"少个功能"，是**会错**。

**挂起项二 —— 补跑过去日期的数据污染（2026-10-09 查明，已修打分部分）**

表头补跑按钮要求 `POST /main-force/refresh?date=<过去某天>`，但 `mainforce.run()`
混用了 as-of 与「当前」两套数据。根因是 `quotes.market_snapshot()` 抓的**当前**行情，
而补跑的目标日已经过去。

| 环节 | 取值基准 | 状态 |
|---|---|---|
| 涨跌停池 `get_zt/dt_pool(trade_date)` | as-of | ✅ |
| 资金流 `_collect_inflow(..., trade_date)` | as-of | ✅ |
| 逐只日线 `_fetch_histories(..., trade_date)` | as-of | ✅ |
| 位置维度 `_dim_price_position`（用 `hist.close.iloc[-1]`） | as-of | ✅ |
| **维度 5「换手适中」`_dim_turnover`（权重 10）** | 原当前 → **as-of** | ✅ **已修** |
| **输出行 `price`/`pct_chg`/`turnover`/`amount`** | 原当前 → **as-of** | ✅ **已修** |
| 全市场快照 `quotes.market_snapshot()` | 当前 | — 污染源头 |
| → 粗筛 `_coarse_filter` 停牌 / 成交额 | 当前 | ❌ 剩余 |
| → 粗筛 `_coarse_filter` ST 判定 | 当前 | ❌ 剩余 |
| → 粗筛 `_coarse_filter` 流通市值过滤 | 当前 | ❌ 剩余 |
| → **候选池预选 `_preselect`**（决定哪 300 只拉日线） | 当前 | ❌ 剩余 |
| → 输出行 `float_mv` | 当前 | ❌ 剩余 |

**已修的做法**：新增 `_asof(hist, trade_date, field)` —— 取日线里**恰好等于**
`trade_date` 那一行的字段，**严格按日期匹配而不取 `iloc[-1]`**：那天停牌时末行会落在
更早的日期，取末行等于拿前几天的值冒充当天，比退回快照更糟。缺行返回 `None`，
由调用方退回快照。`_score` 与 `_dim_turnover` 因此各多接收一个 `trade_date`。

**关键的非回退保证**：正常跑当天若日线还没更新到当天（盘中 / 刚开盘），
`_asof` 回 `None` → 退回快照 → 与改动前行为完全一致。

**为什么今天才暴露**：`?date=` 参数前端一直没用过（`mainForceRecompute()` 从不带日期），
这个潜伏问题今天才被表头补跑按钮第一次触发。

**为什么剩余部分难改**：粗筛与预选都跑在 `_fetch_histories` **之前**，那时逐只日线
根本还没取回，拿不到 as-of 的换手 / 市值。要改就得把日线获取提前到粗筛之前 ——
候选量从约 300 变成约 3000，取数量翻 10 倍，且**内网下无法验证**（要真实跑一轮对比）。

**修后影响评估**：打分与展示字段已按该日历史还原；残余偏差集中在「选出哪 300 只」
（预选里换手权重仅 0.15，而主力资金流是 as-of 的主导项）与粗筛的 ST / 停牌判断，
故补跑历史日的候选集仍可能与当日实跑有出入。

### T+1 误差复盘（同批落地）

**落库是 `/api/fund-estimate` 唯一的副作用**（纯本地 SQLite、零网络）：`fund_estimate_log`

### 首屏回读上次结果（2026-10-10 落地）

**用户的问题原话**：「基金查到的估值数据为什么没保存，现在每次打开都得查一次，我觉得
应该把查到的数据存起来，不要一进页面就空着。」

**澄清一件事：数据一直是存着的**。`fund_estimate_log` / `fund_nav_log` 每次点「查询估值」
都在写（就是上面 T+1 复盘那两条流水）。真正缺的是**回读**——`/api/fund-estimate` 只算实时、
从不读库，所以首屏 `data === null`，页面只能空着等用户再点一次。补的是这一步，不是存。

#### `GET /api/fund-estimate/last` + `db.fund_last_estimates()`

**只读本地 SQLite、一个网络请求都不发** —— 所以能跟着首屏一起拉，**仍然满足
「不点查询估值就不发包」**：读本地库不算发包。返回结构与 `/fund-estimate` 一致（外加
`cached: true`），前端复用同一张表格，零改动。

**三条口径，都是为了「回读出来的一行要和实时查出来的一行长一样，但不冒充实时」**：

1. **只回关注列表里的 code** —— 取消关注的留在流水里（复盘还要用），但不该出现在表格里；
   反过来，关注了却从没查过的**压根不返回**，落到前端 `blankRow`，与「还没查询」一致。
2. **每个 code 只取 `MAX(date)` 那条** —— 回读要的是「上次查到的」，不是整段历史。
3. **净值取 `nav_date ≤ 估算日` 的最近一条，不是「迄今最新」** —— 同一次查询同时写入的
   (估算, 净值) 本来就是这个关系；真取最新的会把 10-10 的净值拼到 10-09 的估算上，
   **两头都对不上**。取不到就 `None`，前端显示「—」，**不补默认值**。

#### 三个诚实标注

- **`cached: true`** —— 前端据此挂一条 info Alert：「下面是上次查询保存下来的结果，不是
  刚查的」+ 落库时刻。**不标就是拿旧数据冒充实时**。
- **`as_of` 是落库时刻、完整到日期**（实时那条给的是 `HH:MM:SS`），因为数据可能来自几天前。
- **`stale` 按归档日 `date` 列算，不能用 `gz_time`** —— 持仓穿透链的 `as_of` 只有
  `HH:MM:SS` 不带日期（`_estimate_date` 就因此退到今天），拿它判会把**当天**的穿透结果
  误标成陈旧。认不出/对不上一律当陈旧，多标一个「非今日」的代价远小于把旧数据当成现值。

`warnings` **恒为空数组**：「数据源降级 N 项」的措辞描述的是取数失败，套在「还没查过」
头上是错的 —— 没查过的 code 本来就不返回。

#### 前端的三点（`FundEstimate.tsx` 的 `loadCached`）

- **走同一个 `seq`**：用户在回读返回前就点了「查询估值」时，迟到的旧结果不能把刚查出来
  的实时值盖掉。
- **`items` 为空不落库**：一只都没查过时保持 `data === null`，那句「点右上角查询估值」
  才还在 —— 否则回读一个空结果会把引导语吃掉。
- **失败只记不弹**：退回「首屏空着」的既有表现，用独立的 `cachedErr` 渲染成 warning
  （不是 `error` 的红色通道，那条是**联网**查询失败专用），避免「读本地缓存没读到」
  看起来像数据源挂了。回读失败也不重试 —— 真故障会由「查询估值」那条路径如实报出来。

### 覆盖率不足与第三方仓库评估（2026-10-14 · **结论：保持现状**）

**用户原话**：「我们的基金估值不准，检查这个仓库 https://github.com/Ye-Yu-Mo/FundVal-Live，
能继承到我们项目中吗。」

#### 实测（`fund_estimate_log` 全量 5 条，`017874 国金量化多策略C`）

| 日期 | 估算 | 实际 | 误差 |
|---|---|---|---|
| 10-12 | -0.7439% | -1.5945% | **+0.8506pp** |
| 10-13 | -0.0761% | +0.1479% | **-0.2240pp**（方向反了） |

5 次查询里 **4 次 `source=持仓穿透`、`coverage=22.95`**，官方估值链没拿到数。
（是「天天基金不给这只基金估值」还是「内网拦了东财」——**日志查不出来**，见下面「已知缺口」。）

#### 根因：coverage 是「防错下限」，不是「可信度下限」

`_holdings()` 用 `topline=10` 只取前十大；量化基金持仓几百只，前十大仅占净值 **22.95%**。
绝对贡献公式 `est% = Σ(wᵢ × rᵢ)/100` 里没取到价的 `wᵢ` 不进求和 —— 剩下 **77.05% 当作 0 涨跌**，
幅度必然系统性偏小。代码自己的 note 就写着「本值通常低于真实涨跌幅」。

10-12 拆开对账（净值按 100 万计）：

| | 占比 | 当天涨跌 | 贡献 |
|---|---|---|---|
| 前十大（取到价） | 22.95% | ≈ -3.24% | -0.74pp ← 算出的 |
| 其余 | 77.05% | ≈ -1.10% | -0.85pp ← **当作 0** |
| 合计 | 100% | | **-1.59pp** ← 实际 |

`_MIN_COVERAGE = 20.0` 的注释原话是「低于这个数**不是算错了就是非 A 股**」——
它是防解析出错的，22.95 属于「**真实但天然不足**」的覆盖，擦线放行给了一个
**技术上没错、实质上没用**的数。同一个数字段扛了两个职责，这才是问题本身。

#### 参考仓库评估：**不能继承，也没有值得抄的算法**

| 它有的 | 结论 |
|---|---|
| `penetration_engine._calculate` 穿透算法 | **同一条链路**，且非 ETF 乘的 `coverage_ratio` 是「披露持仓中**取到价**的比例」而非「占净值比例」→ 三个权重全拿到时 ratio=1，等于把前十大平均涨跌直接当基金涨跌。代入 10-12 得 ≈ **-3.24%**，**比我们更不准**（我们低估一半，它高估一倍） |
| 我们为什么用绝对贡献 | 理由明写在 `_compose` docstring 523-532：归一化后还得再乘一个股票仓位占比，那要多打一次资产配置接口、又是另一张没验证过的 HTML 表。**是刻意取舍，不是漏了** |
| `calculate_accuracy.py` 准度回测 | **我们已有** `metrics/fund_review.py` + `GET /api/fund-review`，还更细（分链、分基金、MAE、最坏、±20pp 丢异常）。属重复实现，不是新增能力 |
| 养基宝扫码 / 小倍养基手机号登录 | 要交出账号 —— 不采用 |
| akshare 全市场估值 | 大依赖，拿的还是天天基金口径的数据 |
| 30s 自动刷新 | 直接违反「基金无轮询无自动刷新」硬基线 |
| Django + PostgreSQL + Celery + Docker | 栈不同；AGENTS 只准抄算法/架构，整仓不可能 |

#### 决策（2026-10-14 用户定）

> **不要没值，允许有误差，coverage 保持现状。**

→ `_MIN_COVERAGE` 留 **20**、公式留**绝对贡献**、宁给偏小的数也**不显示「—」**。
「宁可没数」那个方向被明确否掉。参考仓库**不继承、不引入**。

所以回溯不了「那 4 次为什么落穿透」——日志里 `改走持仓穿透` / `天天基金不提供该基金的盘中估值`

## 7. 添加关注的模糊搜索（2026-10-10 落地）

两个关注页（`/watchlist`、`/funds`）的添加框原来**只认手敲**：用户得先去别处查到
`161725`，回来敲代码、再敲一遍名称。要让它变成「输入名称、点一下」，候选只能来自
**全市场** —— 那就只能联网。

**用户定的两个选择**：

| 问 | 定下来的 | 为什么 |
|---|---|---|
| 数据源 | **联网搜索** | 纯本地只能过滤已关注的，对「新增」这一件事没用 |
| 触发时机 | **防抖 400ms 自动搜** | 比每敲一个字按一次回车顺手；代价是打字过程中会连发外部请求，所以必须配缓存与序号作废（见下） |

### 这是一次**有意的承诺变更**

README 原话是「添加时一次网络请求都不发」。现在拆成两件事，各自诚实：

| 动作 | 路径 | 网络 |
|---|---|---|
| **添加** | `POST /api/watchlist`、`POST /api/fund-watchlist` | **仍然零网络**（纯本地写库） |
| **搜索** | `GET /api/search` | **联网**，防抖 400ms 触发 |

搜索取不到**不影响添加** —— 手贴 6 位代码这条路原样保留，它是搜索挂掉时的兜底，
也是「我不想多发一个包」时的选项。页面上、README 里都按这个口径改了措辞。

### 两个源（2026-10-10 实测）

| 用途 | 源 | 形态 | 实测 |
|---|---|---|---|
| 基金 | 天天基金 `fundsuggest.eastmoney.com/FundSearch/api/FundSearchAPI.ashx`（`m=1&key=`） | **JSON** `{"ErrCode":0,"Datas":[{CODE,NAME,CATEGORY,JP,FundBaseInfo:{DWJZ,FSRQ,FTYPE,JJGS}}]}` | 200 / `charset=utf-8`；代码搜精确 1 条、名称「白酒」4 条 |
| 股票（A 股 + 港股） | 腾讯 `smartbox.gtimg.cn/s3/?v=2&q=&t=all` | **不是 JSON**：`v_hint="市场~代码~\u名称~拼音~类型^…"`，无结果时整串 `v_hint="N";` | 200；`q=600519` 与 `q=茅台` 都回 `sh~600519~贵州茅台`（**代码与名称两种输入都通**）；`q=腾讯` 一并回港股与美股 ADR |

两边都带浏览器 UA + 各自的 `Referer`（`fund.eastmoney.com` / `gu.qq.com`）。

### 过滤：这里最容易出事

**两个源都是模糊匹配，不保证只回你该加的东西** —— 过滤全部落在**字段**上，不看状态码：

| 源 | 会混进什么 | 后果（不滤的话） | 怎么滤 |
|---|---|---|---|
| 基金 | **指数**（`CATEGORY=600`，如「中证白酒」`399997`、`国证白酒` `980031`） | 加进基金列表是**死数据**：查不到估值、也永远不会有净值 | 只留 `CATEGORY=700`，再校一遍 `^\d{6}$` |
| 股票 | **指数** `ZS`、**窝轮权证** `QZ`、**美股** `market=us`、**基金** `market=jj` | 这一页既加不进去、也没有日线 | 只留 `market ∈ {sh,sz,bj,hk}` 且 `type ∈ {GP-A, GP}`，再校位数 |

> **最阴的一条**：**查不到时基金源照样回 10 条**（`ErrCode=0`）。所以 `ErrCode`
> 只能证明「请求成功」，**不能证明「搜到了你要的」** —— 过滤不能依赖状态码。

`market` 参数是给**子菜单**用的（`全部 / A股 / 港股`）：不传，「只看港股」的下拉里会
列出 `600519`，点下去必然 400，还看不出为什么。与其给人一个注定失败的选项，不如
一开始就不给。三个菜单各占一个缓存槽（`stock:any` / `stock:cn` / `stock:hk`），
互不投毒。

### 三道防线扛「防抖连发」

1. **前端防抖 400ms** —— 连续敲字只在停顿后发一次；
2. **后端进程内缓存 10 分钟**（`_CACHE`，按 `(kind, market, 词)` 分键，LRU 上限 200）——
   加完下一只又回头敲同一个词，不再打上游，也**不再累加熔断计数**；
3. **序号作废**（`seq` ref）—— 慢的那个响应后到时序号已经变了，直接丢弃，
   否则会把上一个词的候选盖到当前输入上。

熔断按既有惯例各持一把（`em_fundsearch` / `tx_smartbox`，TTL 10 分钟、连挂 3 次断开），
**与行情源、估值源完全隔离** —— 搜索挂了不该连累估值，反之亦然。熔断打开时返回 `[]`，
**不抛**，页面照常。

### 前端实现的两个坑

- **`react(set-state-in-effect)` 必须守在恰好 6 条**。防抖的「清空候选」和「置忙」
  本来天然要发生在 effect 里，所以它们一律放进 `setTimeout` 回调与 `.then` ——
  那是异步的，规则不管。effect 主体里**只做两件事**：记序号、排 timer。
  实测 `oxlint` 仍是**恰好 6 条**，`SearchPick.tsx` 零新增。
- **antd 的 `AutoComplete` 没有 `onPressEnter`**（它基于 Select，那个 prop 不在类型里，
  tsc 当场拒绝）。改成在外层 `div` 上接 `onKeyDown` —— Enter 从 input 冒泡上来，
  antd 的内部处理先跑，两种情况都对得上。**但不能赌这个次序**（赌错就是同一个代码
  添加两遍），所以 `commit` 打一个 500ms 时间戳，两个入口互相看得见，后到的直接返回。

## 8. 总览页任务进度（2026-10-12 落地）

**问题**：点「立即执行」后只有 `running` 一个布尔值。`steps` 要等 `_finish` 才写进
`_state`，于是「已完成 N 步」在整个 12-15 分钟里恒为 0 —— 页面等于没做进度。

**改动**

| 层 | 改了什么 |
|---|---|
| `scheduler._run_step(live=True)` | 每步**开始**写 `current_step`，**结束**（放 `finally`，失败步也写）落 `steps` |
| `scheduler._run_step(live=False)` | `run_light` 走这条。它与完整流水线**可并存**，不加开关就会把正在跑的进度冲掉 |
| `scheduler._plan()` | 进度条的分母，与 `_collect` **同源生成**，加步骤只改一处 |
| `scheduler.state()` | `steps` 改成**拷贝**（运行中每步在写、`/jobs/status` 每 3s 在读，交内部引用会撞 `dictionary changed size during iteration`）；仅 `current_step == 'main_force'` 时透出 `sub` |
| `mainforce` | 新增 `_PROG` / `progress()` / `_stage()` / `_count()`：`run()` 七阶段各打一点，`_fetch_histories` 逐只计数 |
| 前端 | `JobProgress` 组件（进度条 + 正在做什么 + 已完成清单）；`STEP_LABEL` 独立于 `DATASET_LABEL` |

**两处踩过的坑**

- **`STEP_LABEL` 不能复用 `DATASET_LABEL`**：步骤叫 `sector_industry`
  （`scheduler._collect` 拼的），数据集才叫 `sector_flow_industry`，差一个 `flow`。
- **打分步必须折算**：`main_force` 占八成以上墙钟时间（模块头写明「唯一的 N 次

  死机。故把日线 `x/N` 折成小数加进百分比，并标注「这步最长，约 12-15 分钟」。

### 9.2 关键决策（都不是随手选的）

1. **落库编排搬进 `db`，而不是让 `subscribe` import `routes`** —— `routes` 要用

3. **`_allow` 对绑定的 owner 放行一切（含 `sub`）** —— 否则「试一下」演到

5. **推送与盘后任务共用同一个 scheduler，但各有各的开关**（同日用户推翻
   「共用一个开关」的初稿）—— `scheduler_enabled`（16:30 盘后，缺省**开**，
   既有行为不许改）与 `scheduler_push_enabled`（14:50 推送，缺省**关**）各自
   独立，改哪个都走 `_reconcile()` 重建 job；`POST /api/jobs/schedule` 的
   `enabled` / `push_enabled` 都是可选字段，**不传就不动**，老调用方零影响。
   单开关会逼出「要盘后就必须同时放开 14:50」这种没有道理的耦合。
6. **入口指令必须 `access="any"`** —— `订阅Pro` 要是需要订阅才发得出去，
   未付费用户连开通入口都拿不到，死锁。
7. 测试踩坑：两个订阅者 `created_at` 落在同一秒时，`ORDER BY created_at DESC`
   会退化到按 `open_id` 排 —— 断言得按 `open_id` 对账，不能假设发送顺序。
8. **收银台（2026-10-13 用户改需求）**：`订阅Pro` 不再回虎皮椒占位链接，改回
   **自建收银台** `/pay/<token>` —— 选月份（1/3/6/12，线性价 = `pro_price × 月数`）、
   选支付方式（微信/支付宝）、实时显示金额。**仍不真收款**：没有商户号、没有回调、
   后端只监听本机，「去支付」只生成一张待确认订单，管理员在 `/subs` 照订单点确认
   开通。**这条口径不变** —— 出现真收款入口的唯一条件是支付网关接通且回调能落库。
 9. **定价页面可改（2026-10-14 用户定）**：上面第 8 条那句「线性价 = `pro_price × 月数`」
   现在是**没改时的默认**，不是写死的规则。月单价 / 档位 / 单档金额三层都存
   `kv.pay_pricing`（改完即时生效，不用改 `.env` 也不用重启），某档单独填了就用填的，
   留空才回落线性。`amount_of()` 仍是全站唯一算钱处，收银台、飞书档位表、订单落库
   三处因此不会各算各的。**改价只影响新订单** —— 金额在下单那一刻快照。
   详见 `docs/06` 第五轮。
10. **邀请链接（2026-10-14 用户定）**：**身份是反查出来的，不是点回来的** ——
    点一个裸的 `<a href>` 只发 URL，浏览器不会附带任何飞书身份（飞书在那条链路上
    不在场），所以 open_id 必须在**生成链接那一刻**就烧进 token。结论是**邀请链接
    必须一人一条**，群发一条通用的做不到，那条路要走飞书网页应用 OAuth，而 OAuth
    的重定向 URL 要求 HTTPS + 域名（localhost 配不了），属于 `docs/06 §9` 的 P1。

### 10.4 真机实测记录（2026-10-13 16:19 起，热点）

**已验证为通**：长连接 `connected=true`、收到消息 `handled=1`；lark-oapi CARD 帧补丁**确实生效**

**实翻车一次**：点「发我一张」→ `POST /api/cmds/quick-card` 回 **502**，日志

```
飞书发卡片失败 code=230099 msg=Failed to create card content,
  ext=ErrCode: 300302; ErrMsg: update_multi is false;
```

原因是我按 1.0 的旧习惯把 `config.update_multi` 写成了 `false`（「独享卡片」），而
**Card JSON 2.0 明令只支持 `true`**（2.0 默认值也从 `false` 改成了 `true`）。已改回 `true`
并在 `_card_frame_check.py` 里钉了一条断言，口径写进 `AGENTS.md`。

> ⚠ 后端是 `python -m uvicorn app.main:app --port 8000`，**没有 `--reload`** —— 改完必须重启
> 8000 才生效，热改代码是无效操作。

**实翻车二次**：「指令管理」页的「进快捷卡」「启用」两个开关**点不动** —— 请求其实发出去了，
`POST /api/cmds` **每次都 400**，值被弹回原样，看起来就像没反应。

根因在 `cmdcfg._merged`：

```python
"kind": default.get("kind") or (over or {}).get("kind") or "custom",
```

`BUILTIN` 那 17 条**根本就没有 `kind` 这个键**（它不需要 —— 传了默认定义就必然是内置），
于是内置行一律返回 `kind: "custom"`。前端 `payload()` 照着回传 → `save()` 走「自定义」分支 →
`if key in _BY_KEY: raise "…是内置指令的 key，改它请走内置那条"` → 400。

`kind` 改成**派生值**：`"builtin" if default else "custom"`，且不再从库里那一列合并回来。

> **为什么 121 条断言一条都没抓到**：所有 `save()` 的用例都是**手动传 `kind`** 的，从没有一条
> 把 `rows()` 的输出原样当 payload 喂回去。这是「两个模块各测各的、中间那层往返没人测」的经典
> 漏洞 —— 已补 `_cmd_check` J 段：逐行往返 + 断言内置行必须报 `kind=builtin`。
>
