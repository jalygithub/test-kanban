# 数据源与网络问题排查记录

> 2026-09-27 · M1 阶段实测 · 结论已验证

## TL;DR

1. **AkShare 可用**，涨停/炸板/跌停池、日线、同花顺系资金流全部跑通。
2. **东财 `push2*.eastmoney.com` 家族存在 IPv6 坏节点**（`240e:e1:...` 连接建立后被 RST），需 **IPv4 优先**。
3. **短时间高频请求会被东财限流**（`RemoteDisconnected`），必须**限速 ≥1s + 指数退避重试**。
4. **同花顺、新浪接口不受影响**，可作为资金流的备用源。

## 二、根因分析

### 问题 1：IPv6 坏节点

```
push2.eastmoney.com
  IPv6  240e:e1:8000:1b04::25d   → TCP 建连成功，发送请求后被 RST（读到空响应）
  IPv4  43.144.251.121           → HTTP 200 正常返回
```

**为什么 requests 不自动降级到 IPv4**：Python 的 `socket.create_connection` 按 `getaddrinfo` 返回顺序依次尝试，**只在 TCP 建连阶段失败时才换下一个地址**。坏 IPv6 节点 TCP 能连上，但 HTTP 层被重置 → urllib3 抛 `RemoteDisconnected`，**不会触发地址切换**，请求直接失败。

同域名对比（同一次测试内）：

| 域名 | IPv6 | IPv4 |
|---|---|---|
| push2.eastmoney.com | RST ❌ | 200 ✅ |
| push2ex.eastmoney.com | 正常 | 正常 |

> 注：`push2ex` IPv6 正常，说明**不是整机 IPv6 不可用**，而是 `push2` 家族的部分 v6 节点有问题。因此**不能一刀切禁用 IPv6**。

**修复**：`socket.getaddrinfo` 包装为 **IPv4 优先排序**（保留 IPv6 作为回退，不删除）。

### 问题 2：限流

排查期间高频连发请求后，`push2*` 全家族返回 `RemoteDisconnected`，**强制 IPv4、等待 180s、切换 header 均无效**；同时段同花顺 / 新浪 / push2ex 仍正常。

→ 判定为**针对 push2 家族的 IP 限流**，与地址族无关。

正常项目节奏（每天几十次、每次间隔 1s+）不受影响；本次是排查时连发 150+ 次触发的。

### 问题 3：读超时只管「单次 recv」，挡不住滴流响应

`requests` 的 `timeout=(connect, read)` 里 **`read` 是每次 `recv()` 的上限**，不是整次请求的上限；urllib3 2.x 也只在建连时 `sock.settimeout()` 一次，之后整条连接沿用这个值。

服务端只要每次 `recv` 都在 read 秒内回哪怕 1 字节，超时就永不触发 —— `Content-Length` 没读满就一直等下去，请求**永久挂起**。盘后定时任务一旦撞上，就再也醒不过来。

复现（本地滴流服务端，0.3s/字节，`Content-Length: 1000000`，客户端 `timeout=(2,2)`）：

```
未装 netfix：    /trickle  HUNG >6.0s（守护线程仍在阻塞）
装总时长闸门后： /trickle  raise Read timed out. (3.01s)
                 /slow     ok 200 (1.52s)   ← 1.5s 后完整返回，没被误杀
                 /fast     ok 200 (0.00s)   ← 紧接着的请求，deadline 已还原
```

**为什么闸门要落在 `settimeout` 上**：HTTPS 走 C 层 `SSL_read`，**根本不经过 Python 的 `recv`**，改调用方式管不到它；只有套接字上的 `SO_RCVTIMEO` 能穿透到 C 层。所以做法是给每次请求挂一个绝对截止时刻，`recv` / `recv_into` 前把套接字超时收紧到剩余预算，预算耗尽直接抛 `socket.timeout`。

**为什么是 120s**：`_m4_full.log` 里最慢的单次成功请求约 35s（腾讯日线偶发 23~35s，常态 1.7s），留 3 倍余量。误杀的代价只是这一路失败、交给多源回退接管；而挂死不可恢复。可用 `STOCK_REQUEST_TOTAL_TIMEOUT` 覆盖。

**为什么不会误伤同进程的 uvicorn**：闸门只在「有活动截止时刻」且「套接字是阻塞模式」时介入，两者缺一即原样放行；`_DEADLINE` 又是线程局部的，事件循环线程根本读不到值 —— 双保险。

### 问题 4：东财逐日资金流 daykline 必须走 `http://`，而且一连发就被封 IP

「近 5 日总流入」要逐日明细，唯一能一次拉 5 天的是东财 `push2his` 的
`/api/qt/stock/fflow/daykline`（akshare 对应 `stock_individual_fund_flow`）。
这里有两个坑：

**坑 1：同一个路径，`https://` 连不上，`http://`（80 端口）能通。**
装好 netfix（IPv4 优先 + 总时长闸门）之后做 A/B，同样参数各打 3 次：

```
https://push2his.eastmoney.com/...  → RemoteDisconnected ×3
http://push2his.eastmoney.com/...   → 200 ×3，JSON 正常
```

所以 `quotes.stock_fflow_daykline()` 里 `_EFFLOW_URL` 是**写死 `http://`** 的；
akshare 内部硬编码 https，`ak.stock_individual_fund_flow` 在本环境不可用，只能自己发请求。

字段顺序（实测固定）：

```
[日期, 主力净额, 小单净额, 中单净额, 大单净额, 超大单净额,
 主力净占比, 小单净占比, 中单净占比, ...]
```

两条可用来抓解析错误的不变量：`主力 = 大单 + 超大单`，`主力 + 小单 + 中单 = 0`。

**坑 2：`push2*` 家族按客户端 IP 限流，触发后 http/https 一起死。**
排查期间连发 100+ 次后：

| 现象 | 说明 |
|---|---|
| `http://push2his...` 返回 `{"rc":102,"data":null,"message":"请求异常"}` | 服务端主动拒绝，不是网络错误 |
| 之后再打 → `ConnectionError` / `RemoteDisconnected` | 连 TCP 都不给建了 |
| `push2delay` / `push2ex` / `1.push2his` / `4.push2his` 同一路径 | 全部 `rc:102` —— **换子域躲不掉，是 IP 级** |
| 13 分钟内每 90s 探 1 次（`_probe_ab.py`，9 个采样点） | 全 FAIL，限流窗口远比想象的长 |

正常项目节奏（每天几十次、间隔 1s+）碰不到；本次是排查时连发触发的。

**兜底**：`stock_net_inflow` 本来就该**每天盘后落一行**攒出来 —— 封禁解除前，
16:30 的定时任务照常抓当天，5 个交易日之后窗口自然就满 5 天；前端只在
`missing > 0 && backfilling` 时才提示「逐日资金流回补中」，不阻塞列表渲染。

**坑 3：内网下这条回补会变成一个停不下来的外网请求循环。**

公司网把 `push2*` 在建连期直接 RST，回补于是每次都 `fetched=0`：撞上 45 秒预算 →
`fetched==0 and need>0` → 写入 10 分钟冷却 → 冷却一到，只要 MainForce 页还开着，
下一轮又来了。**每 10 分钟一批、单批 28 只 × 3 次重试，全被安全设备拦截并记录**
（实测 `backend.log`：`10-08 10:12`、`10-09 10:59 / 11:11 / 13:01 / 13:19 …` 一律
`{'need': 28, 'fetched': 0}`）。它从 09-30 就存在，不是某次改动引入的。

开关（`app/config.py` 的 `inflow_backfill`，默认 `true`）：

| `.env` 取值 | 行为 |
|---|---|
| `STOCK_INFLOW_BACKFILL=false` | **任何路径都不再发外网资金流请求**：`/main-force/inflow` 的后台回补线程、飞书推送成功后的关注股回补、飞书「关注列表」的前台现查（2026-11-07 新增：缺数先补再返回，预算 10s/10 只） |
| 不写（默认 `true`） | 与之前完全一致 —— 有网时它确实管用（`10-08 10:12 fetched=9`） |

改完重启后端生效。关掉后 `missing` 照常返回（列表该显示 `-` 还显示 `-`），
但 `backfilling` 恒为 `false`，前端据此**停止轮询** —— 连本机那 40 次 × 1.5s 的
空转也省了；悬停在 `-` 上会写明「回补未启用或冷却中」并点出开关名。
三处入口 `_start_inflow_backfill`（routes.py）、`_backfill_watch_inflow` 与
`watch_block` 前台现查（都在 notify.py）都在**发请求之前**拦截，
所以关掉时一个 `connect()` 都不会发生。

验证：`_inflow_switch_check.py`（socket 层封死非回环连接）——
默认值为 `true`、`false`/`0` 两种写法都能覆盖、关掉时不调 `backfill_inflow`
且 `running` 不被置位、打开时仍照旧起线程（行为未变）、冷却逻辑未被开关破坏、
notify 入口直接 return、**非回环连接 0 次**，全过。

## 三、落地的防御措施

写入 `backend/app/netfix.py`，在任何 AkShare 调用前 import：

| 措施 | 实现 |
|---|---|
| **IPv4 优先** | 包装 `socket.getaddrinfo`，AF_INET 排前，不删除 AF_INET6（保留回退） |
| **限速** | **按域名分桶 + 随机抖动**：普通源 0.35s + 0~0.5s，东财 push2 系 1.5s + 0~2s（全局 1s 曾把同花顺 105 页分页拖到 105s；固定匀速又最容易被当成机器请求） |
| **默认超时** | `Session.request` 层统一补 `timeout=(5.05, 30)`，调用方显式传了不覆盖 |
| **总时长闸门** | 每次请求挂绝对截止时刻（默认 120s），`recv`/`recv_into` 前把套接字超时收紧到剩余预算。**read timeout 只管单次 recv，挡不住滴流响应**（见「问题 3」） |
| **指数退避** | 失败重试 3 次，1.5s/2.5s/4s + 随机抖动 |
| **坏页重试** | 同花顺快照链把 akshare 的**解析**异常（`AttributeError`/`ValueError`/`KeyError`/`IndexError`）也纳入 `retry_on`，`base_delay` 抬到 3s —— 热点/限流下返回的非数据页是**偶发**的（10-09、10-12 同接口都正常 5200+ 行），重抓即可。两源皆挂时抛带**双方原因**的 `RuntimeError`，不再把 akshare 天书异常直接透进 `job_run.detail`（见 2026-10-13 `main_force` 连挂两次的复盘） |
| **数据源熔断** | 按源计连续失败，达标即熔断 10 分钟（`em_fund_flow` / `em_hist` / `tx_hist`…） |
| **数据源回退** | 行情/资金流优先东财，失败转同花顺 / 腾讯 / 新浪；板块资金流优先同花顺 |
| **快照兜底** | 实时接口失败 → 读本地历史快照 → 仍无 → demo 数据 |
| **接口隔离** | 所有 AkShare 调用集中在 `fetchers/`，上游改名只改一处 |

## 四、可复用的验证脚本

```python
import socket, requests
_orig = socket.getaddrinfo
def v4first(h, p, family=0, type=0, proto=0, flags=0):
    r = list(_orig(h, p, family, type, proto, flags))
    r.sort(key=lambda x: 0 if x[0] == socket.AF_INET else 1)
    return r
socket.getaddrinfo = v4first

print(requests.get(
```

## 六、M4 打分流水线的规模化实测

M4 一轮要逐只拉 300 只日线，是全项目对网络最重的一次压力，结论与单点验证不同：

**1. 东财被挡的范围比预想大。** 不只是 `push2` 的行情与资金流，`stock_zh_a_hist`
走的 `push2his` 同样 `RemoteDisconnected`（TCP/TLS 能建连，HTTP 层被 RST）。
也就是说打分流水线的**实际主力日线源是腾讯** `stock_zh_a_hist_tx`，东财只是首选。

**2. 熔断是必须的，不是优化。** 东财每次失败要先吃 2 次指数退避（约 5s）才认输。
若 300 只逐只请求每次都先试一遍东财，光失败就多耗 20 分钟以上；
连续失败 3 次熔断 10 分钟后，后续请求直接走腾讯。

**3. 腾讯日线的规模参数**（`history_days=400` 自然日，覆盖 250 个交易日）：

| 项 | 实测 |
|---|---|
| 每只返回行数 | ≈ 268 根（上市更晚的更少，低至 227 根） |
| 单只耗时 | 1.7s 正常；偶发重试最坏 45s |
| 300 只纯取数 | 8-9 分钟 |
| 一轮端到端（含快照/粗筛/打分） | **12-15 分钟** |

**4. 偶发抖动可被重试完全吸收。** 日志里反复出现 `ConnectionError` 与
`ReadTimeout`，重试 1-2 次后全部成功，**300 只成功 299 只（99.7%）**，
唯一失败的 `002252` 三连失败后被跳过。日志里偶尔冒出的
`数据源熔断 em_hist` 是预期行为，不是故障。

**5. 无大单分解是结构性缺失。** 同花顺 `stock_fund_flow_individual` 只给净额，
没有超大单/大单拆分，因此东财不可用时维度 3（大单净额占比）覆盖率恒为 0%，
整维弃用、权重从 100 降到 85 —— 这是数据源决定的，不是 bug。
