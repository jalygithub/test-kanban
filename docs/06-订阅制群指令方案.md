### 2.1 为什么链接带 token 而不是 open_id

URL 会进浏览器历史、聊天转发记录与 nginx access log。把 `ou_xxx` 直接写进去
等于到处撒身份标识，而且链接被转发后谁都能替他下单。

`pay_token` 是一张随机串映射表，随机串**不可逆推**身份、**过期即作废**。
顺带一提：`open_id` 也**不出现在收银台接口的返回里** —— 页面要的只是昵称与
到期时间，少回一个标识就少一处泄露面（截图、浏览器扩展都拿得到）。

### 2.2 为什么仍不真收款

真收款要三样现在都没有的东西：商户号、支付回调、能被手机访问到的公网地址。
在这三样齐之前放一个「看起来能付」的入口，结果就是**用户真付了钱而系统不知道**
—— 这是纠纷，不是功能缺失。所以 `去支付` 只生成订单，页面上明写
「演示环境：不会真正扣款」。

**这条口径不变**：任何时候都不许出现真收款入口，除非支付网关接通并且回调
能落库。

## 3. 数据模型（六张新表：订阅 3 + 收银台 2 + 邀请 1，**不动** `fund_watchlist` / `watchlist`）

```sql
CREATE TABLE subscriber (
    open_id     TEXT PRIMARY KEY,          -- 飞书 open_id
    nickname    TEXT NOT NULL DEFAULT '',
    plan        TEXT NOT NULL DEFAULT '',  -- '' = 未订阅, 'pro'
    paid_at     TEXT,                      -- 本次订阅起算
    expires_at  TEXT,                      -- paid_at + 30 天
    amount      REAL,                      -- 金额（占位价，可手改）
    fund_limit  INTEGER,                   -- 空 = 用全局 fund_watch_limit
    created_at  TEXT NOT NULL
);

-- fund_watchlist 现状是 code 主键 = 全局关注，多用户必须另起
CREATE TABLE subscriber_fund (
    open_id   TEXT NOT NULL,
    code      TEXT NOT NULL,               -- 6 位基金代码
    name      TEXT NOT NULL DEFAULT '',
    added_at  TEXT NOT NULL,
    PRIMARY KEY (open_id, code)
);

CREATE TABLE push_log (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    open_id   TEXT NOT NULL,
    kind      TEXT NOT NULL,               -- 'fund_1450' / ...
    sent_at   TEXT NOT NULL,
    ok        INTEGER NOT NULL,
    detail    TEXT NOT NULL DEFAULT ''
);

-- 收银台两张表（2026-10-13，§2 第四轮）。**同样是占位**：没有支付网关、
-- 没有回调，订单只在「管理员照着它点开通」这一步有用。
CREATE TABLE pay_token (
    token      TEXT PRIMARY KEY,           -- 随机串，不可逆推 open_id
    open_id    TEXT NOT NULL,
    nickname   TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL               -- 过期即失效，链接不永久有效
);

CREATE TABLE pay_order (
    order_no     TEXT PRIMARY KEY,          -- P + 时间 + 随机尾巴
    open_id      TEXT NOT NULL,
    nickname     TEXT NOT NULL DEFAULT '',
    months       INTEGER NOT NULL,          -- 1 / 3 / 6 / 12
    price        REAL NOT NULL,             -- **下单那一刻**的单价快照
    amount       REAL NOT NULL,             -- price × months
    channel      TEXT NOT NULL,             -- 'wechat' / 'alipay'
    status       TEXT NOT NULL DEFAULT 'pending',  -- pending / done / closed
    token        TEXT NOT NULL DEFAULT '',
    created_at   TEXT NOT NULL,
    confirmed_at TEXT,                      -- 管理员点确认的时刻
    note         TEXT NOT NULL DEFAULT ''
);

-- 邀请链接（2026-10-14，§11）。**与 pay_token 并列而不复用**：收银台那条链路
-- 已跑通且有回归，为省一张表给 token 加 kind 再分流不划算。
CREATE TABLE invite_token (
    token      TEXT PRIMARY KEY,
    open_id    TEXT NOT NULL,
    nickname   TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL
);
```

**金额快照**是刻意的：之后管理员改 `pro_price` 不该把历史订单的金额一起改掉，
否则「他当时付了多少」这个问题就没有答案了。

## 4. 权限层：指令注册表 + **默认拒**

### 为什么必须先有闸再加指令

现状 `feishu.dispatch:471-479` 是**唯一一道闸**，一个 `if` 同时干了「认证」（绑定没）
与「授权」（是不是 owner）。下面十几条 `if t in (...)` **各自不校验** —— 结构上是
**default allow**：订阅制一开，任何一条忘过闸的新指令，未付费用户直接就能用。

> **顺序不可反**：先有闸，再加指令；反过来就是漏。

### 两个易踩的坑

1. **飞书不走 HTTP** —— 长连接 WebSocket 回调，压根不经过 router。
   这层**不能**做成 FastAPI middleware，只能是**函数级入口闸**。
2. **权限只看 `sender_id`，绝不看会话类型** —— 否则「私聊绕过群里校验」就是漏洞。
   私聊/群聊只决定**回复发到哪**，不决定能不能执行。

### 设计

```python
_CMDS: dict[str, dict] = {
    "帮助":    dict(fn=..., access="any"),    # 未订阅也能用
    "订阅Pro": dict(fn=..., access="any"),    # 必须免费，否则死锁（拿不到开通入口）
    "基金":    dict(fn=..., access="sub"),
    "关注基金": dict(fn=..., access="sub"),
    "删除基金": dict(fn=..., access="sub"),
    "关注列表": dict(fn=..., access="sub"),
    "跑":      dict(fn=..., access="owner"),  # 超管专用，订阅者不给
}
# dispatch = 解析 → 认证(open_id) → 授权(access) → 执行
```

| access | 含义 |
|---|---|
| `any` | 任何人（含未订阅、未绑定） |
| `sub` | `subscriber` 里 `plan='pro'` 且 `expires_at > now` |
| `owner` | `sender_id == feishu_owner` |
| 缺失 / 不在表里 | **拒绝**（默认拒） |

**必须尊重**现有 `allow_side_effects=False`（「试一下」按钮不许因为新权限层真跑任务）。

### 分层

```
L0 解析（是不是指令）      现有 _clean + 正则
L1 身份（你是谁）          open_id 有没有绑定
L2 授权（你能不能执行）    any / sub / owner        ← 本方案新增
L3 资源限制（能拿多少）    fund_limit 超限提示
```

### HTTP 侧暂不加

后端只监听本地/内网，飞书订阅者拿不到地址，加了是空转。
**触发条件**：一旦 API 对外暴露（买服务器 + nginx 开放），立刻补 —— 记 `docs/04 §9` 待办。
另注：backlog #6 `/api/system/stop` 公网是雷属**暴露面**问题，与订阅权限两码事，不混改。

## 5. 指令表

| 指令 | access | 行为 |
|---|---|---|
| `帮助` | any | 现有 HELP + 新增三条 |
| `订阅Pro` | any | 回**收银台链接**（带随机 token）+ 档位价目；已订阅则回「已订阅，X 日到期」 |
| `开通 <open_id> <金额>` | owner | **人工开通**（占位链接无回调，靠这条）—— P0 唯一开通路径 |
| `基金 <6位>` | sub | `fund_estimate.estimate()` 双链 → 文本化估值 |
| `关注基金 <6位>` | sub | 写 `subscriber_fund`；先查 `fund_limit`，超限回「关注数量超出」 |
| `删除基金 <6位>` | sub | 删 `subscriber_fund`；不在关注里回「未关注该基金」 |
| `基金关注`（别名 `我的基金`） | sub | 列出该用户关注基金 + 实时估值 |
| `跑` / `轻跑` / `状态` / `摘要` / `候选` / `板块` / `查询` / `关注 <股票>` / `取关 <股票>` | owner | **保持现状不变** |

**正则顺序**（关键）：新增的 `基金|关注基金|删除基金` 必须排在 `^(?:查询|查|看)?\s*(\d{6})$`
与 `^(?:取关|…|删除|移除)\s*(\d{6})$` **之前**，否则会被旧分支吃掉。

## 6. 14:50 推送

- **触发**：`scheduler` 加第二个 cron（`CronTrigger(hour=push_hour, minute=push_minute)`，
  默认 `14:50`），`is_trade_day()` 为假直接跳过
- **对象**：`subscriber` 中 `plan='pro'` 且未过期、且 `subscriber_fund` 非空的用户
  （没关注的不发，不骚扰）
- **通道**：`feishu.send_text(open_id, text, id_type='open_id')` —— **私聊**，不进群
  （`notify.send` 是 webhook，发到固定一处，按用户分发用不了它）
- **内容**：每只基金一行 `名称 代码 估值涨跌幅 估值净值(估值时间)` + 免责声明
- **落库**：`_record_fund_logs`（与 `/fund-estimate` 同一条路），顺带攒 T+1 复盘样本
- **留痕**：每次发送写 `push_log`，失败重试 1 次，仍失败 `ok=0`
- **兜底**：启动时已过 14:50 且当天没推过 → 只告警不补发（与 `_warn_if_missed_today` 同口径）

## 7. 订阅管理菜单

**路由** `/subs`，页面 `pages/Subs.tsx`，图标 `CrownOutlined`，
插在「定时任务」与「数据管理」之间（`App.tsx` 的 `ITEMS` + `<Routes>`）。
**owner 专属**，订阅者看不到。

**列表列**：open_id · 昵称 · 订阅时间 · 到期 · 金额 · 状态 · 关注基金 `3/10` · 最近推送 · 推送成功/失败

**行内操作**：开通/续期(30天) · 关闭 · 单独设关注上限 · 展开看关注明细与推送历史

**接口**：`GET/POST /api/subs` · `POST /api/subs/{open_id}` ·
`GET /api/subs/{open_id}/funds` · `GET /api/subs/{open_id}/pushes` ·
`GET/POST /api/subs/pricing`（收银台定价，2026-10-14）

> ⚠ `/subs/pricing` 必须注册在 `POST /subs/{open_id}` **之前** —— 两条都是两段路径，
> 注册晚了就被 `{open_id}="pricing"` 抢走。`_sub_check` 有对应回归。

**收银台定价卡片**（2026-10-14 加）：月单价 · 可增删的档位 · 各档金额
（留空 = 月单价 × 月数）。**自己拉自己存** —— 不从父组件接 `pricing` 再同步，
那样得在 effect 里 setState，`react(set-state-in-effect)` 全站基线恰好 6 条加不了第 7 条。

**收银台订单卡片**（2026-10-13 加）：订阅者在收银台下的单列在这里，
**只有 `pending` 行有「确认开通」按钮** —— `done` 再点一次会把订阅期间累加两遍，
是真实会发生的操作事故，所以前端不给按钮、后端也用 409 挡着，两头都拦。

**收银台接口**（`app/pay.py` + `routes.py`）：

| 接口 | 谁用 | 说明 |
|---|---|---|
| `GET /api/pay/plans` | 收银台页 | 档位 + 支付方式（**不带 token**，档位是公开信息） |
| `GET /api/pay/{token}` | 订阅者 | 首屏：昵称、到期、档位、他自己的订单。**不回 open_id** |
| `POST /api/pay/{token}/order` | 订阅者 | 下单。金额**不在请求里传**，后端按 `amount_of(months)` 算并快照（页面显示与订单落库同一个口子） |
| `GET /api/pay/orders` | 管理员 | 待确认订单列表 |
| `POST /api/pay/orders/{no}/confirm` | 管理员 | 照订单开通；重复确认 409 |

> ⚠ **路由注册顺序**：`/pay/orders` 必须排在 `/pay/{token}` **之前**。
> 两条都是两段路径，注册晚了会被 `{token}="orders"` 抢走，管理员的订单列表直接 404。

**收银台页面**（`pages/Pay.tsx`，路由 `/pay/:token`）：**整页脱离后台布局**。
它是订阅者本人用手机打开的，套上 `<Sider>` 就等于把「停止服务」按钮
（后端 `/api/system/stop` 目前无鉴权）暴露给每个订阅者。所以 `App.tsx` 在
`<Layout>` 之前用一个正则把 `/pay/` 前缀摘出去单独渲染。

## 11. 邀请链接（2026-10-14 用户定）

与收银台**并列**的一条链路：收银台是「订阅者自己发指令 → 拿到自己的链接」，
邀请是「owner 从名单里选人 → 生成链接发给对方 → 对方点开直接免费开通」。

**链路**：

    攒名单（二选一）
      · 飞书长连接收到消息 → sub_upsert 落一行（plan='' = 还没订阅）
      · owner 手工 POST /api/invite/join 填 open_id（**不调飞书接口**）
    owner 在订阅管理页「邀请开通」卡片点「生成链接」
    对方点开 /invite/<token> → 欢迎页（后端从 token 反查出昵称）
    点「订阅」→ subscriber 落 plan='pro' + pro_days 天 + amount=0

**为什么必须一人一条链接**：点一个裸的 `<a href>`，浏览器发出去的就只有 URL
本身，**不会附带任何飞书身份**（飞书在那条链路上不在场）。所以身份必须在
**生成链接那一刻**就烧进 token。群发一条通用链接谁点都一样，后端面对的是匿名
请求 —— 那条路要走飞书网页应用 OAuth，而 OAuth 的重定向 URL 要求 HTTPS +
域名，localhost 配不了（§9 的 P1 待办）。

**几个决定**：

| 项 | 决定 |
|---|---|
| 存哪 | `invite_token` 表，**与 `pay_token` 并列而不复用** —— 收银台那条链路已跑通且有回归，为省一张表给 token 加 `kind` 再分流，不划算 |
| 名单 | **就是 `subscriber` 表**，不另开表。`plan=''` 是「在名单里、还没订阅」，`plan='pro'` 是已订阅。一张表两个状态，不存在「名单里有但他其实已经订了」这种要对账的状态 |
| 名单怎么进 | 两条入口，都落 `sub_upsert`。① `feishu._handle_event` 收到消息 —— **不是多调一次飞书接口**，open_id 本来就在长连接推来的事件里；② `POST /api/invite/join` 手工填（**一行飞书接口都不调**）—— 长连接在内网连不上时，①收不到东西，这是唯一入口 |
| 金额 | `amount=0` 就是免费标记。**不加字段、不迁移**，订阅管理页把 0 显示成「免费」 |
| 天数 | 与付费订阅同一个 `pro_days`（30 天） |
| 重复点 | 只回状态、**不重复累加天数** —— 否则把链接转给别人点两下，30 天就翻倍了。与 `pay.confirm_order` 用 409 挡重复确认同一个理由 |

**接口**（`/invite/list` 与 `/invite/make` 必须注册在 `/invite/{token}` 之前，
与 `/pay/orders` 是同一个被路径参数抢走的坑，`_sub_check` 有回归）：

| 接口 | 谁用 | 说明 |
|---|---|---|
| `GET /api/invite/list` | 管理员 | 名单（`subscriber` 全表）+ `pro_days` |
| `POST /api/invite/join` | 管理员 | 手工把人加进名单。**一行飞书接口都不调**，`open_id` 自己填 |
| `POST /api/invite/make` | 管理员 | 给某人生成一条。**每次都是新的一条**，旧的到各自过期为止 |
| `GET /api/invite/{token}` | 被邀请人 | 欢迎页首屏。**回昵称、不回 open_id**（同 `/pay/{token}`） |
| `POST /api/invite/{token}/activate` | 被邀请人 | 免费开通；已在订阅期只回状态 |

**页面**：`pages/Invite.tsx`（路由 `/invite/:token`），与 `Pay.tsx` 一样
**整页脱离后台布局** —— 被邀请人不该看到那个无鉴权的「停止服务」按钮。

**已知局限**：名单靠攒，而**飞书长连接在公司内网根本连不上**
（`ConnectionResetError 10054`），所以「收到消息自动落一行」那条入口现实中收不到
东西，名单会一直空着。补救是 `POST /api/invite/join` —— owner 在订阅管理页手工填
open_id 加人，**一行飞书接口都不调**。要「谁点都能订」（免手工、免攒），得先有
HTTPS 域名再上飞书 OAuth。

**链接前缀**：收银台与邀请链接共用 `pay.base_url()` —— 默认 `http://localhost:5173`
**手机打不开**（手机上的 localhost 指手机自己）。电脑连手机热点时在订阅管理页
「链接前缀」卡片里换成电脑的局域网 IP（`ipconfig` 看，形如 `http://192.168.137.x:5173`），
**存 `kv` 即时生效，不用改 `.env` 也不用重启**；同时 `vite.config.ts` 的
`server.host` 已打开（原来只听 loopback）。⚠️ 代价：同网络设备都能访问本服务，
而 `/api/system/stop` 目前无鉴权。

**推送链接**（`POST /api/invite/push`）：名单里点「发给他」= 生成一条链接 **并用
飞书私聊发给那个人** —— `feishu.send_text(open_id, text, id_type="open_id")`，与
长连接无关（那条是**收**消息的，这里是**发**）。**不发群 webhook**：链接一人一条、
token 里烧的是生成时那个人的 open_id，进了群谁点开都把订阅开通到**他自己**头上。
`sent=false`（凭据 / 应用权限 / 对方不可达）时**链接照样返回**，页面上留着可复制
手发 —— 不让「发不出去」把「拿到链接」一起废掉。

**页面分四页签**（2026-10-14 拆，原来一屏五张卡要滚动）：① 已订阅 ② 邀请开通
③ 收银台 ④ 定价与链接；免责声明在页签外，任何页签下都看得见。
