# A股盘后复盘看板

盘后一屏回答三个问题：**板块资金去哪了**、**谁涨停谁跌停**、**谁可能在偷偷建仓**。

> ⚠️ 仅用于数据整理与可视化研究，不提供投资建议，不构成任何买卖依据。

## 快速开始

### 0. 一键启动（桌面，推荐）

日常使用走这个：**双击桌面上的「A股看板一键启动」**（桌面还没有图标时
先跑一次 `py -3 scripts\start_all.py shortcut` 生成一个）。启动过程**完全
静默** —— 不弹黑色控制台窗口，日志写进 `run\`，两个服务就绪后自动打开
浏览器 <http://localhost:5173>。

```powershell
py -3 scripts\start_all.py start        # 起后端 + 前端（已在跑的跳过），就绪后开浏览器
py -3 scripts\start_all.py start --no-open   # 只起服务，不开浏览器
py -3 scripts\start_all.py stop         # 按 run\services.json 的 PID 杀整棵进程树
py -3 scripts\start_all.py status       # 看两个端口 / PID / 日志路径
py -3 scripts\start_all.py shortcut     # 在桌面生成「A股看板一键启动」快捷方式
```

- **日志**：`run\backend.log`（后端 uvicorn + APScheduler）、`run\frontend.log`
  （vite）、`run\start.log`（每次起停的记录），进程 PID 记在 `run\services.json`
  —— 整个 `run\` 已进 `.gitignore`。
- **关闭**：页面左侧菜单**最下方**的「停止服务」按钮（危险色、有确认弹层），
  点完先出「服务已关闭」结束屏，之后端口 8000 / 5173 都会释放；顺序上是
  **先回响应再杀进程**，否则按钮永远拿不到结果。盘后任务正在跑时接口返回
  409 拒绝，免得把 12-15 分钟的打分打到一半作废。
- 停完再用（双击快捷方式或 `start`）就能恢复，页面上点
  「我已重新启动，刷新页面」即可。

> 端口探测用 `localhost` 而不是 `127.0.0.1`：vite 默认只监听 `::1`，
> 只探 IPv4 会把「已经在跑」误判成「没起」，于是又拉一个、白撞端口。

### 1. 后端

```powershell
cd backend
py -3 scripts\manage.py setup     # 建 .venv + 装依赖
py -3 scripts\manage.py doctor    # 体检：依赖/网络/数据库
py -3 scripts\manage.py fetch     # 抓一次数据（约 30s）
py -3 scripts\manage.py start     # 启动 http://127.0.0.1:8000
```

API 文档：<http://127.0.0.1:8000/docs>

### 2. 前端

```powershell
cd frontend
npm install
npm run dev          # http://localhost:5173
```

Vite 已配置 `/api` 代理到 8000 端口。

### 3. 生产构建

```powershell
# 后端
backend\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# 前端
npm --prefix frontend run build
```

### 4. 部署到服务器

本地 Docker 打包成离线镜像、scp 上阿里云（香港节点，免备案）、`docker compose` 起
nginx + 后端 —— 完整流程、验收清单与备份见 **`docs/03-本地打包与服务器部署.md`**，
部署件在 `deploy/`。定时任务的开关存在 SQLite 里，迁移数据即自动继承；
服务器上用手动触发（页面「执行一次」或飞书发 `跑`）。

| GET | `/api/watchlist/{code}/series` | 关注详情：建仓日前后日线 + 区间表现 + 同期沪深300 + 后续再入选 |
| GET | `/api/realtime?codes=&detail=` | **实时行情**（关注页第二个 Tab）：只查 `codes` 里这些代码，**不扫全市场**（上限 50 只）。A 股 / 港股分两批走腾讯 `qt.gtimg.cn` 批量报价，资金流再取一批，`detail` 那一只另取 `web.ifzq.gtimg.cn` 分时。**逐字段过不变量校验**（涨跌额 ≈ 现价−昨收、最高 ≥ 现价 ≥ 最低、成交额 ≈ 成交量×价格…），过不了置 `null` 并进 `warnings` —— 宁可前端显示「—」也不返回猜出来的数；三个源各有独立熔断，失败只降级自己那一块，不 5xx |
| GET | `/api/fund-estimate?codes=` | **盘中基金净值估算**（「基金估值」页，**手动触发、不轮询**）：只查 `codes` 里这些，上限 30 只。两条链 —— ① **天天基金官方估值** `FundValuationLast`（**一次批量**取回全部 code，主域挂了自动切备域）：`|gsz/nav − 1| ≤ 20%` 才认（抓数量级错误，**不是**旧的 `gszzl ≈ (gsz/nav−1)×100` —— 新口径下两者基准不同），`nav` 缺失则整条链判失败转 ②；② **持仓穿透**：上一季前十大重仓股 × 它们此刻的涨跌幅（行情直接复用 `/api/realtime` 那条腾讯批量链），算**绝对贡献** `Σ(wᵢ×rᵢ)/100` 并回传覆盖率。三道门拦着第二条链：列序靠特征互证不写死、有效持仓 ≥ 3 只、取到价的覆盖 ≥ 20%（QDII / 债基会在这儿被拦下，而不是算出个接近 0 的错数）。**每个 code 都回一行**，两条链都失败时该行全字段 `null` + `warnings` —— 不 5xx，也不拿假数顶上。每行另带 `display_pct` / `display_kind` / `display_reason`：按时段决定涨跌幅这一列此刻显示估算还是实际（见「涨跌幅那一列显示谁」） |
| GET | `/api/fund-watchlist` | 关注基金列表（本地 SQLite，**不联网**） |
| POST | `/api/fund-watchlist` | 添加基金 `{"code": "161725", "name": "…"}`：**纯本地写库**，名称留空也照样成功；名称等第一次查估值时由后端回填（**只补空的**，手填的优先于接口给的） |
| DELETE | `/api/fund-watchlist/{code}` | 取消关注；不在列表返回 404 |
| GET | `/api/fund-review` | **T+1 误差复盘**：把历史盘中估算和事后公布的真实净值对起来。**只读本地 SQLite，一个网络请求都不发** —— 所以页面首屏就能拉，不违反「不点查询就不发包」。某天既有估算、又有前后两个真实净值（间隔 ≤ 5 个自然日）才算一个样本；误差 = 估算涨跌幅 − 实际涨跌幅（**正 = 高估**）。两条链**分开统计**；误差超 ±20pp 的样本按取数/日期归属出错丢弃，并**在 `notes` 里计数**（不静默消失） |
| GET | `/api/fund-estimate/last` | **上次查到的估值**。**只读本地 SQLite，一个网络请求都不发** —— 流水本来每次查询都在写（给上面那张复盘表攒样本），缺的只是回读这一步，于是每次打开都得重新查一遍、首屏空着。回读补上后首屏直接有数，**且仍然满足「不点查询估值就不发包」**：读本地库不算发包。结构与 `/fund-estimate` 一致外加 **`cached: true`**，页面据此挂「这是上次查询的结果」，**不冒充实时**。每个 code 只回**最近那天**的估算；净值取 `nav_date ≤ 估算日` 的最近一条（**不是**迄今最新 —— 那会把明天的净值拼到昨天的估算上）；`stale` 按**归档日**判（穿透链的 `as_of` 只有 `HH:MM:SS`，拿它判会误标）；`warnings` 恒空（「降级 N 项」描述的是取数失败，套在「还没查过」头上是错的）。`display_*` 三个字段照样有 —— 实际涨跌幅改从**本地净值流水**现算（查询时回填的历史），仍然零网络 |
| GET | `/api/stock/{code}/daily?days=&refresh=` | **个股日线**（详情页「走势」）：东财 → 腾讯回退，进程内缓存 30 分钟；两个源都挂时返回 `rows=[]` + `error`（不 5xx，页面其余部分照常显示） |
| GET | `/api/news?category=&refresh=` | 财经新闻：六源聚合 + 主题分类 + 自算热度（进程内缓存 5 分钟；跨源同闻自动合并成一条；六源全挂才回退内置演示数据 `demo=true`） |
| GET | `/api/data/usage` | **数据占用画像**（只读、零网络）：库文件 / 各表 / 按 dataset 的字节与日期范围 / 日志大小 / `job_run` 残留 / 保留策略与硬下限。`kv` **只回键名**，值（飞书 App Secret、webhook 签名密钥）不回传 |
| POST | `/api/data/purge` | 清理，`scope=snapshot \| retention \| job_run \| vacuum \| log`。**默认 dry_run 只算不删**；真删要 `dry_run=false` **且** `confirm="DELETE"`，少一个返回 400。硬下限内的日期进 `blocked` 拒删 |
| GET | `/api/replenish/status` | 历史补录四个 job（`bars`/`inflow`/`pools`/`score`）的状态与进度。**零联网**，只读内存状态 |
| POST | `/api/replenish/start` | 起一个补录 job（后台线程）。⚠️ **会联网**且是几百到上万次请求量级 —— 只在「历史补录」页的按钮触发；断点续跑，原样再点一次就是续跑 |
| POST | `/api/replenish/stop` | 优雅停止补录 job（票/批边界退出，已落库的都保留） |

> 打分单轮要逐只拉 ~300 只日线（每只 268 根），实测 **约 12-15 分钟**（口径取自 `job_run` 表：8 次完整打分 12.3~15.4 分，2026-09-27 起；重新核对就查这张表，别凭印象改），
> 因此**写操作走后台线程**：`POST /refresh` 立即返回，前端轮询 `status`。
> `GET /api/main-force` 只读缓存，绝不阻塞在 HTTP 请求里 —— 打分期间
> 依然返回上一轮结果，跑完才覆盖。

### 盘后定时任务

每交易日 **16:30** 由 APScheduler 触发（非交易日自动跳过），依次跑
涨停 / 炸板 / 跌停 / 强势池 → 行业 / 概念板块资金流 → 主力建仓打分。
每一步独立 try，结果按 `success / partial / failed` 记进 `job_run`（含 `kind`
区分 `scheduled` / `manual`）。冷启动时如果**已经过了 16:30 只打告警不自动补跑**，
要补数据用 `POST /api/jobs/run` 或总览页的「立即执行」。

开关在左侧菜单的「**定时任务**」页：除了开 / 关，还能手动「立即执行」与
「强制重跑」，下面挂着运行历史（哪次是定时触发的、耗时多少、哪一步失败）。
开关存在 SQLite 的 `kv` 表里 —— 关掉之后重启后端**不会**自己开回来
（`scheduler.start()` 启动时先读这个键）。

### 跑完通知（飞书 webhook）

`app/notify.py`：**在定时任务（`job_run.kind = scheduled`）和飞书指令（`kind = feishu`）
跑完后**推一条到飞书自定义机器人；页面上手动「立即执行」、盘中轻量抓取都不发
（那两个场景人就在屏幕前，响一声反而是噪音）。

手动跑完还想收一条 → 点同一张卡片上的**「推送摘要」**（`POST /api/jobs/notify/digest`）：
状态、触发方式、失败步骤全取自 `job_run`，与自动推送同源。它**不受「跑完通知」开关约束**
—— 开关管的是自动推送，人在页面上主动点了发送是另一件事；webhook 地址仍然必须已保存。

正文是纯文本，一段一行。**除框架外每段都可勾选**（见下「推送内容勾选」）：

- 标题 + 任务行（成功 / 部分失败 / 失败 · 用时）—— **始终推送**
- 涨跌停家数与最高连板（`pools`）
- 疑似主力建仓 Top10（**名字 + 代码 + 近 5 日主力净流入**，口径写在段标题里；
  分数、涨跌幅、理由文本都不推；该股没有资金流记录给 `-`；
  打分日不是目标日时会标注）（`mainforce`）
- 行业板块资金流**净流入 / 净流出 TOP5**（板块口径是**亿元**，与个股资金流的「元」不同，
  混用会把 8.6亿 显示成 8.6元）（`sector`）
- 关注股票：当日涨跌幅 + 近 N 日主力净流入（N 取库内实际覆盖天数，不足窗口就如实写几天）
  （`watch`）
- 失败步骤（若有）（`failed`）+ 免责声明 —— **免责声明始终推送**

个股主力净流入**只有一个口径**（`notify._inflow_by_code`）：窗口 = 目标日及之前、
库内已有的**最近 5 个交易日**，逐日累加。主力建仓段、关注段、飞书「查询」与网页端
`/api/main-force/inflow` 全部走它，N 跟着 `scorer.yaml → metrics.inflow_window_days` 走。

**不要**改成「按该股自己的记录取最近 N 条」来凑满 5 天 —— 那样缺一天就往后够，
够多远没有上限。实测 20260929 抓取失败（全库仅 30 行），荣盛发展缺当天记录，
于是够到 6 个交易日之前的 20260924，把那天 -1.01 亿 的流出算进「近5日」，
推送显示 +2670万 而页面显示 +1.28亿。固定窗口有缺口时只**少算**，
`days` 如实反映覆盖了几天，缺口由 `inflow_gaps` 报给网页端自动回补。

正文取的全是库内数据；唯一可能的网络请求是「关注股当日涨跌幅库里查不到」时补拉一次日线
（20 秒预算 + try 兜底，拿不到显示 `-`）。发送排在任务状态落定**之后**执行，
`after_job` 把拼装与发送的异常全部吞掉只记日志 —— **通知挂了绝不影响任务本身**。
发送成功后还会在后台线程回补关注股的逐日资金流缺口（40 秒预算），让下一条消息数据更全。

#### 推送内容勾选

「跑完通知」卡片上的勾选框决定发哪几段，**改了立即保存生效**（存 SQLite 的
`notify_sections`，重启后端也保留）。分段清单与文案由后端
`notify.SECTION_DEFS` 下发（`GET /api/jobs/notify` 的 `section_defs`），
以后加一段正文只改那一处，页面自动多一个勾选框。

三条行为约定：

1. **未升级的老库 = 全选**，行为与没有这个功能时完全一致。
2. **标题、任务状态行、免责声明是消息框架，不参与勾选**，永远推送 —— 一段都不勾时
   正文只剩这三样，页面会给「一段都没勾」的黄色提示。
3. **没勾的段连数据都不查**（分段构造是惰性的）：不勾 `watch` 就不会触发补拉日线的
   网络调用，省掉最多 20 秒。

飞书入站的「摘要」指令走同一个 `build_digest`，所以手机上发「摘要」拿到的内容
与页面勾选一致；要单独看某一段，发「主力」「板块」「关注」指令即可，那三条不受勾选约束。

配置在「定时任务」页的「跑完通知（飞书）」卡片：填地址、可选签名校验密钥、开关、
**推送内容勾选框**、「测试发送」按钮（按库内最新数据立刻发一条，正文回显成预览，
飞书返回的 `code=19024` 关键词不匹配 / 签名校验失败等错误原样显示）、「推送摘要」按钮
（发的是最近一轮任务的真实结果，不是测试消息 —— 两者的区别是「测试发送 · 测试成功」
与「手动执行 · 成功」）。地址与密钥存在 SQLite 的
`kv` 表（`notify_webhook` / `notify_secret` / `notify_enabled` / `notify_sections`），
改了不用重启后端。`POST /api/jobs/notify` 的 `sections` 字段**省略即保持现有勾选**，
传 `[]` 表示一段都不推 —— 所以只改地址的老调用方不会意外把勾选清掉。

飞书机器人安全设置三选一，都要在这里配对才发得出去：

| 安全设置 | 要做的 |
|---|---|
| 自定义关键词 | 正文要含关键词；不含就回 `code=19024`，测试按钮会把这行原文回给你 |
| IP 白名单 | 把本机出口 IP 加进机器人白名单 |
| 签名校验 | 把密钥填进「密钥」框，后端按 `timestamp + "\n" + secret` 算 HMAC-SHA256 再 base64 |

### 飞书入站指令（手机遥控）

`app/feishu.py`：**收**飞书消息。和上面的出站推送同叫「飞书」，方向、凭据、机制完全不同：

| | 出站 `notify.py` | 入站 `feishu.py` |
|---|---|---|
| 凭据 | 自定义机器人 webhook（POST 一个 URL） | 企业自建应用 `app_id` + `app_secret` |
| 方向 | 项目 → 飞书群 | 飞书 → 项目 |
| 机制 | 发一条 HTTP | 事件订阅 `im.message.receive_v1` |
| 网络要求 | 无 | **长连接（WebSocket）：本机主动连出去，不需要公网 IP、不用内网穿透** |

选长连接而不是回调 URL 的原因：回调要公网可达（本地得做内网穿透），长连接是本机主动建连 ——
家里电脑、云服务器、NAT 后面都一样能收。回消息用同一个应用的 `im/v1/messages`（SDK 自己取并
缓存 `tenant_access_token`），**不复用出站 webhook**：那个只能发到它所在的群，而收到的指令
可能来自单聊或别的群，回错地方比不回更糟。

收到文本后按指令分发：

| 指令 | 干什么 |
|---|---|
| `订阅Pro` | 回**收银台链接**（选月份 1/3/6/12、选微信/支付宝、金额实时显示）；已订阅则回到期日与已关注数 |
| `基金 161725` | 该基金实时估值（**要订阅期内**） |
| `关注基金 161725` | 加进**我自己的**关注，超限回「关注数量超出」（上限可按人单独设） |
| `删除基金 161725` | 取消关注，只动 `subscriber_fund`，**不碰网页端的 `fund_watchlist`** |
| `基金关注` | 我关注的基金与它们的实时估值 |
| `开通 <open_id> [金额]` | **owner 专用**人工开通 / 续期 —— 收银台不接支付网关、没有回调，这是 P0 唯一的开通路径（收银台订单走 `/subs` 页的「确认开通」） |
| `状态` | 上次任务 / 下次定时 / 涨跌停池、打分、板块三个数据集的新鲜度 |
| `跑` | 完整盘后流水线（后台线程，约 12-15 分钟），**跑完自动把摘要推回这个会话** |
| `轻跑` | 只抓涨跌停池 + 板块资金流；先回一句「抓取中」，完成后**再单独报一次**结果 |
| `摘要` / `候选` / `板块` | 复盘正文与其中的分段（`build_digest` 与 `mainforce_block` / `sector_block` / `watch_block` 同源，文案只有一处） |
| `查询 600825` | 是否在池（含连板数）、现价涨跌、候选打分与排名、近 5 日主力净流入、是否已关注；也支持按名称模糊查（`查询 博纳`） |
| `关注 600825 [20260928]` | 加关注：建仓日缺省取该股最近打分日，取不到再退回当日池子日期 |
| `取关 600825` / `关注列表` | 取消关注 / 关注股的当日涨跌与主力净流入 |
| `帮助` | 指令清单 |

**三档权限**，登记在 `feishu._ACCESS`，**默认拒** —— 认不出的文本、或认出了却
没登记 `access` 的指令，一律走不到执行段（新增指令忘填 = 拒，不是放行）：

| 档 | 谁能用 | 指令 |
|---|---|---|
| `any` | 任何人（含没绑定、没订阅的） | `帮助`、`订阅Pro` —— **入口必须免费**，否则没订阅的人连开通入口都拿不到，死锁 |
| `sub` | `subscriber` 里 `expires_at` 还没到的 | `基金`、`关注基金`、`删除基金`、`基金关注` |
| `owner` | `owner` 里那个 `open_id` | 其余全部：`跑` / `查询` / 股票的 `关注`·`取关` / `开通` …，群友喊「跑」一律回「无权限」 |

`owner` 本人**放行一切档位**（哪怕自己没订阅）—— 否则「试一下」演到订阅指令只会
得到一句「请先订阅」，超管反而被自己的系统挡在外面。`owner` 为空时 owner 档的指令
只回「你的 open_id 是 …」让人照着填（第一次接入就是靠这句拿 open_id）。
**权限只看 `sender_id`，与私聊 / 群聊无关**：私聊和群里能发的完全一致，会话类型
只决定回复发到哪 —— 看会话类型就等于给「私聊绕过群里校验」开洞。非文本消息回一句
「只认文字指令」，机器人自己发的事件直接丢弃，不会形成回环。

**交易日 14:50** 把每个人关注基金的实时估值**私发**给他（`scheduler` 的第二个 cron，
**与盘后任务各有各的开关**：盘后 16:30 那个缺省开、14:50 推送这个缺省关，互不牵连，
「定时任务」页两个 Switch 各管一摊；非交易日、交易日历不可用一律不发）。每次发送
都落 `push_log`，成没成与失败原因在 `/subs` 页可见；没关注基金的订阅者不发，不骚扰。
盘中拿不到当日净值，推的是**实时估值**；正文带免责声明。

**收银台**（`pages/Pay.tsx`，路由 `/pay/:token`）：发「订阅Pro」拿到的链接落在这里。
页面上选**月份**（1 / 3 / 6 / 12，金额 = 单价 × 月数，线性不打折）与**支付方式**
（微信 / 支付宝），实时显示应付金额。三件事必须知道：

- **链接里没有 `open_id`，只有一个随机 token**（`pay_token` 表映射，有效期
  `pay_link_days` 默认 30 天，过期即 404）。URL 会进浏览器历史、聊天转发与
  nginx 日志，裸 `open_id` 等于到处撒身份标识；接口返回里也**刻意不带它**。
- **点「去支付」不会扣款** —— 没有支付网关、没有回调、后端只监听本机/内网。
  它生成一张**待确认订单**并给出订单号，页面明写「演示环境：不会真正扣款」。
  管理员在 `/subs` 页的「收银台订单」卡片核对后点**确认开通**，按订单月份顺延到期。
  **重复点确认会被 409 挡下**（否则连点两次订阅期间累加两遍）。
- **页面整页脱离后台布局**：订阅者用手机打开它，套上侧边栏就等于把「停止服务」
  按钮（后端 `/api/system/stop` 目前无鉴权）暴露给每个订阅者。

**这条口径不变**：任何时候都不许出现真收款入口，除非支付网关接通且回调能落库。
用户真付了钱而系统不知道，是纠纷而不是功能缺失。
`pay_base_url` 默认 `http://localhost:5173`，买服务器后要改成公网域名，
并把 nginx 的 `auth_basic` 从 `/pay/` 摘掉，否则订阅者会被口令框挡在门外。

生命周期与可靠性：

- 凭据 / 开关存 `kv`（`feishu_app_id` / `feishu_app_secret` / `feishu_owner` /
  `feishu_inbound`），保存立即生效，**不用重启后端**。
- 起连接前先**预检**一次 `tenant_access_token`：`app_id` 打错时 SDK 会掉进无限重连、
  页面上永远显示「运行中」，预检把飞书返回的 `code/msg` 直接显示在卡片上
  （连不上时会显示 `连不上 open.feishu.cn：…`，一眼看出是网络问题）。
- 长连接跑在守护线程里，事件处理再丢一层线程 —— 卡住 SDK 的事件循环就收不到后面的消息、
  还会掉心跳。启停靠「代数」标记，在途的旧事件直接丢，不会串到新一轮连接。
- **副作用只发生在真实消息里**（`跑` / `轻跑` / `关注` / `取关`）。页面上的「试一下」走
  `POST /api/feishu/simulate`：同样的分发逻辑，但 `allow_side_effects=False`，
  只回「会做什么」，调试时不会把一整轮打分跑起来。
- 卡片上的「**发我一条**」走 `POST /api/feishu/push`：反过来验证**出站**——
  应用主动推一条看板状态到白名单那个人的单聊（owner 为空则退而求其次发到机器人
  所在的第一个群，都没有就如实报错）。收发两条链路都能一键自测。

开放平台侧一次性配置：open.feishu.cn → 创建「企业自建应用」→ 添加机器人能力 →
事件订阅选**使用长连接接收事件** → 订阅 `im.message.receive_v1` → 发布版本 →
把 App ID / Secret 填进「定时任务 → 飞书指令（手机遥控）」卡片。
群里发言要 `@机器人`，单聊直接发即可。

### 逐日主力净流入的回补

`stock_net_inflow` 是**每天盘后落一行**攒出来的，冷启动只有 1 天，而 §8.3 维度 1
和「近 5 日总流入」列都要 5 天。`GET /api/main-force/inflow` 发现覆盖不足时，
会在**后台线程**里逐只从东财 daykline 回补最近 5 个交易日并合并写回
（按日期 load → 按 code upsert → save，不会冲掉当天其余 4725 行），
用响应里的 `missing` 告诉前端还差几只，**且 `backfilling` 为 `true` 时**前端才轮询
（回补被关掉或正在 10 分钟冷却中时它恒为 `false`）。
接口本身**只读 DB、不发网络请求**（起的是后台线程），所以首屏 30ms 就能返回。

**内网下想一个外网请求都不发**：`backend/.env` 写 `STOCK_INFLOW_BACKFILL=false`
再重启后端。公司网把 `push2*` 在建连期直接 RST，回补永远 `fetched=0` 却仍每
10 分钟重试一批（实测 28 只 × 3 次重试），**这批请求会被安全设备拦截并记录**。
关掉后 `/main-force/inflow` 的后台回补线程与飞书推送成功后的关注股回补都
**不再起**（两处都在起线程之前拦截，一个 `connect()` 都不会发生）；`missing`
照常返回、`backfilling` 恒为 `false`，前端随即停止轮询，「总流入」列显示 `-`
并悬停说明原因与开关名。默认 `true`（有网时它确实管用），详见 `docs/02` 问题 4。

## 关注股票

左侧菜单的「关注股票」是个**子菜单**，下挂三个入口，共用同一份数据、同一个页面，
只是过滤口径不同：

| 子菜单 | 过滤口径 | 说明 |
|---|---|---|
| 全部 | 不过滤 | 混排，港股行带蓝色 `HK` 标签、现价前缀 `HK$` |
| A 股 | `market=cn` | 建仓日 / 当时排名 / 当时分三列齐全 |
| 港股 | `market=hk` | 摘掉排名与打分两列（模型不跑港股，永远是 `-`），标题注明「同期基准 = 恒生指数」 |

**两种关注方式**：

1. 在「主力建仓候选」页点行首的星标 —— A 股候选专用，关注时把**当时的候选快照**
   （六维分 + 入选理由 + 排名）一并存下，之后可以回看「当时为什么关注它」。
2. 在关注页顶部那个框 —— 它**既能搜也能直接贴代码**：

   - **搜**：输代码或名称，停顿 400ms 自动出候选，点一下就加。走的是腾讯
     `smartbox`（同一份数据覆盖 A 股与港股），**这一步会联网**，结果后端缓存 10 分钟。
     子菜单限定了市场时候选也跟着限定，不会在「只看港股」里列出 `600519`。
     下拉里会把已在关注列表的标成「已添加」，指数、窝轮权证、美股与基金行一律滤掉。
   - **贴**：直接敲代码回车。搜索挂了、或想加的偏偏搜不到，这条路照旧通 ——
     **落库本身仍然是纯本地、零网络**。

   名称留空时自动去腾讯行情查（约 50ms），查不到就用代码兜底，**绝不因此关注失败**。
   代码位数是硬校验：在港股页贴 6 位代码会直接 400，不会存成一条自己都看不见的假关注。
   这是港股的唯一入口 —— 打分模型只跑 A 股，港股不会出现在候选里。

> 手动关注没有「建仓」这回事，页面上相应位置标的是**起算日**而不是建仓日。

详情页包含：

- **日K（近 90 日）** —— 多取建仓日之前 90 个自然日做上下文。这是必须的：候选是盘后刚
  算出来的，**建仓日几乎必然是最新交易日**，只从建仓日起取图上只有一根K线。
- **区间表现** —— 基准价取建仓日收盘（候选盘后产出，能拿到的下一个价就是它），统计区间
  严格从建仓日起算，与上下文无关。
- **累计收益率对比** —— 个股与基准都以起算日为 0%，同图可比，超额收益直接读差值。
  基准按市场选：**A 股 = 沪深300，港股 = 恒生指数**（后端 `metrics/track.py` 按
  `market` 分键缓存）。
- **关注时的候选快照 + 后续是否再次入选 Top30**（港股与手动关注显示「不适用」说明）。

> **研究性工具**：本功能只呈现已发生的客观行情与当时打分，不预测后市，不构成买卖依据。
> 关注本身没有任何筛选含义，历史走势不代表未来收益。

数据缓存 6 小时，用「刷新表现」按钮可强制重拉。指数对比取不到时自动降级为「-」，
不影响个股数据。港股不提供涨跌停池、连板梯队、板块资金流与个股资金流 —— 详情页对应
区块显示「不适用」而不是空图表。

## 基金估值（盘中）

左侧**新顶级菜单**，与「关注股票」是两回事：基金代码恒 6 位、和 A 股代码撞格式但语义
完全不同，存的也是两张表（`watchlist` vs `fund_watchlist`）。硬塞进关注股票的子菜单，
反而会让 `/watchlist/cn` 那套按位数判市场的逻辑去接 6 位基金代码。

**两步都不轮询、不自动刷新**：

1. **添加** —— 左边那个框**既能搜也能直接贴 6 位代码**：
   - **搜**：输代码或名称（如 `161725` 或 `白酒`），停顿 400ms 自动出候选，点一下就加。
     走天天基金 `fundsuggest`，下拉里会标出基金类型与公司（**A/C 份额要分清**，选错
     多付销售服务费），已在关注列表的标成「已添加」。**这一步会联网**，结果缓存 10 分钟。
   - **贴**：敲代码回车，名称框填了就用、留空交给后端回填（**只补空的**，手填的优先于
     接口给的）。搜索取不到也不影响这条路 —— **落库本身仍然纯本地、零网络**。
2. **查询估值** —— 点一次发一次。**不点「查询估值」，一个估值包都不发**。
   （上面那个候选搜索是另一码事：它是添加的一部分，只在**打字停顿**时触发，
   不打字就一个包都没有。）

**打开页面时还会自动回读一次上次查询的结果**（`GET /api/fund-estimate/last`）——
这不是第三步，因为它**只读本地 SQLite、一个网络请求都不发**：流水本来每次查询都在写
（给下面那张复盘表攒样本），缺的只是回读这一步，页面才每次打开都空着。回读回来的那一屏
顶上会挂一条提示，写明「**下面是上次查询保存下来的结果，不是刚查的**」并给出落库时刻
（完整到日期，因为数据可能来自几天前）；`stale` 仍按归档日标「非今日」。**从来没查过就
仍然空着**，提示也还是原来那句「点右上角查询估值」—— 不拿任何默认值去填。

### 三条链

| 链 | 来源 | 能给出 | 拿不到就 |
|---|---|---|---|
| **官方估值** | 天天基金 `FundValuationLast`（JSON，**一次批量**；主域 `fundcomapi.tiantianfunds.com` → 备域 `fundcomapi.eastmoney.com`） | 估算净值 + 估算涨跌幅 + 正式净值 + 净值日期 + 估值时点 + **名称** | 转下一条链 |
| **持仓穿透** | 上一季前十大重仓股 × 它们此刻的涨跌幅（行情复用 `/api/realtime` 那条腾讯批量链） | 涨跌幅 + 覆盖率 | 标红「未取到」 |
| **净值历史** | 天天基金 `pingzhongdata/{code}.js`（akshare `fund_open_fund_info_em`「单位净值走势」，逐只拉，整轮共用 8s 预算 + 进程内半小时缓存） | 最近 40 个净值日 + **日增长率**（源给的现成实际涨跌幅） | 该轮不显示实际，**估值照常** |

- **官方估值换过一次源（2026-07-21 换的，原接口下线）**：旧的 `fundgz.1234567.com.cn/js/{code}.js`
  因监管要求**全量 301 到错误页**，且**HTTP 仍是 200** —— 光看状态码会被骗成「取数成功」，
  只有解析响应体才能识破。现在走天天基金 H5 在用的 `FundValuationLast`：正经 JSON、支持
  `FCODES` 批量、带主备域。
- **自洽校验换过判据**：新源的 `nav` 是 `PDATE` 那天**已公布的净值**，而 `gszzl` 相对的是
  上一交易日 —— 盘后与周末两者基准不同，`(gsz/nav−1)` 与 `gszzl` 的差值**恰恰就是估值误差
  本身**。旧的 `gszzl ≈ (gsz/nav−1)×100`（容差 0.05pp）在新口径下会把所有基金都判死，所以
  换成 `|gsz/nav − 1| ≤ 20%`：抓得住小数点错位与单位错乱（那种会差几倍），抓不住零点几个
  百分点的口径差。**`nav` 缺失则整条链判失败** —— 那等于没有任何交叉验证，转下一条链。
- **「这只基金不提供估值」与「取数失败」是两回事**：部分主动管理型基金 `gsz`/`gszzl`/`gztime`
  三个字段是 `null`，但**名称、正式净值、净值日期照给**。这时会给出一条独立可读的 warning、
  并把名称与净值**留给持仓穿透那一行**（穿透只算得出涨跌幅，给不出这两样），而不是含混地
  报成取数失败 —— 后者会让你以为接口又挂了。
- **持仓穿透只给涨跌幅，不给估算净值**：算涨跌幅不需要昨收，算净值需要，而昨收恰恰只有
  官方那个接口才有 —— 两条链挂一个才轮到另一条，所以拿不到。这一格就老老实实显示「—」。
- **穿透链的公式是绝对贡献** `Σ(wᵢ×rᵢ)/100`（wᵢ = 占净值%、rᵢ = 当日涨跌幅%），**不是**
  归一化加权平均：后者估的是「股票部分的涨跌幅」，要还原成基金涨跌幅还得再乘一个股票仓位
  占比 —— 而那个占比要多打一次没验证过的资产配置接口、又是另一张 HTML 表。绝对贡献不需要
  它，算出来的就是**前十大重仓股对基金净值的实际贡献（百分点）**，每个输入都能自证，缺的
  部分明确体现在「覆盖率」里，不靠一个假设去补。所以这个数**通常低于真实涨跌幅**，页面上
  写清楚了。
- **三道门拦着第二条链**（任一不过就判失败、显示「未取到」）：列序**不写死**，靠「第 2 格是
  6 位数字」与「有且仅有一个格以 % 结尾」互相印证，坏行过半放弃整张表；有效持仓 ≥ 3 只；
  取到价的覆盖 ≥ 20%（前十大正常占 40~60%）。
- **只认 6 位 A 股代码**：港股/美股在天天基金持仓表里长什么样本环境没验证过，宁可不计入，
  也不能把 `00700` 当 A 股丢给行情接口 —— 查出来的是别的东西。QDII 因此会被「覆盖 ≥ 20%」
  那道门拦下，由债基/QDII 自己的口径决定显示「未取到」，而不是算出个接近 0 的错数。
- **估值时点不是今天就打「非今日」标**：周一早上源还挂着上周五的估值是常态。**不把值抹掉**
  （抹掉反而像接口挂了），连同时间一起显示，由你自己判断。
- 两个东财系接口（估值、持仓 `fundf10`）**熔断各自独立**，也与腾讯行情的熔断独立 ——
  公司网下东财被 RST 时一次都通不了，共用熔断会把本来能用的腾讯行情一起判死。估值那条链
  自己还带**主备域**：主域失败直接换备域再试，两次都失败才计熔断。
- **持仓那条链要带 `Referer` + UA**：`fundf10` 有 WAF，实测无请求头 → 404，`Referer` 域名
  写成 `fund.eastmoney.com` → **514**，只有 `Referer = https://fundf10.eastmoney.com/` +
  浏览器 UA 才回 200。参数 `topline=10&year=&month=` 也是实测能拿到持仓表的那一档。
- **第三条链只为「显示谁」服务**：估值源只带**一个** `NAV`+`PDATE`，算实际涨跌幅要两个。
  盘前要给前一交易日、盘后要判当日机构净值出没出，都得看历史 —— 拿不到就让那一列退回估算，
  **绝不用估算冒充实际**。拉到的序列会回填本地 `fund_nav_log`，于是首屏回读（零网络）也能
  自己算出实际涨跌幅；复盘的净值侧也从「必须 D+1 再点一次」放宽成「净值公布之后点过一次
  查询就补齐」。它与估值链、持仓链的熔断**各自独立**，挂了不连坐。

### 涨跌幅那一列显示谁

「估值跟实际差 1 个点」是常态（估算本来就不是净值），真正的问题是**没说此刻该信谁**。
后端按时段算好并把理由一起返回，前端只负责把它标出来：

| 时段 | 显示 | 为什么 |
|---|---|---|
| 交易中 / 午间休市 | **估算** | 当日净值还没公布，只有估算在动 |
| 盘前 | **前一交易日的实际** | 那时的估值是昨天的尾巴，没有参考价值 |
| 已收盘 | 当日机构净值**出了 → 实际**，没出 → **估算** | 收盘后先等净值，等不到就用盘中估算顶着 |
| 非交易日 | 最近一次公布的净值 | 今天不会有新净值 |

每行带 `display_pct` / `display_kind`（`estimate` / `actual` / `none`）/ `display_reason`；
页面挂一枚「估算 / 实际」Tag，悬停能看到**估算与实际各自的时点** —— 不带时点地把两个数并排，
正是「差 1 个点」变成困惑的来源。两条都没有就显示「—」，**不编一个 0**。

判定只看**时钟 + 本地交易日历缓存**（`_is_trade_day` 读不到缓存回 `None`、退回只看时钟），
不联网 —— 否则 `/api/fund-estimate/last` 的零网络承诺就被这条判定打穿了。

### T+1 误差复盘

同一张页面下方的第二张表。它回答的是**这个估算到底能不能信**，只用已经发生过的数据，
不做任何预测 —— 也就不需要你额外做任何事：照常点「查询估值」，样本自己会攒起来。

| | |
|---|---|
| **误差定义** | `估算涨跌幅 − 实际涨跌幅`，单位是**百分点（pp）**而不是百分比。正 = 高估，负 = 低估 |
| **实际涨跌幅怎么来** | 用天天基金公布的单位净值，前后两日相除 |
| **为什么叫 T+1** | 估值源的 `nav` 只带**一个**净值日期（`pdate`），而算涨跌幅要两个；第二个要等当天收盘后才公布。**换源没有改变这一点** |
| **零网络** | `/api/fund-review` **只读本地 SQLite**，首屏就能拉 —— 不点「查询估值」它也照样有历史数据 |

样本闭合的节奏：

```
D 日点查询   → 记下 D 日的估算（fund_estimate_log）
D+1 日再点  → 接口带回 D 日净值，D 日的样本闭合
```

**五条口径，页面上原样摊给用户**：

1. **「真实净值」也是天天基金公布的**，不是基金公司公告原文 —— 这个复盘衡量的是
   「我们的估算 vs 天天基金的净值」，中间还隔着一层数据源。
2. **样本是自选的**：只在你手动点查询的日子留下估算，漏点的日子就是没有。这不是连续
   序列，别当成一份完整的统计报告。
3. **两条链分开统计**：官方估值覆盖完整但口径黑箱；持仓穿透只覆盖前十大重仓股里的
   A 股部分、系统性偏低。混在一起算出来的平均值谁都不代表。
4. **误差超 ±20pp 的样本直接丢弃并计数**：这个量级几乎一定是取数或日期归属出了问题
   （比如把跨周末的两天当成相邻两天），留着会把均值拉到毫无意义的位置。丢弃的数量进
   `notes`，**不会静默消失**。
5. **相邻净值间隔 > 5 个自然日就不算样本**：跨周末最多 3 天，再加法定长假也够；再大
   说明中间漏了净值，算出来的是多日累计而不是当天涨跌幅。

**样本 < 5 条时标「样本少」** —— 那个平均值基本是噪声，页面上明说，别据此下结论。

- **落库是 `/api/fund-estimate` 唯一的副作用**：纯本地 SQLite、零网络，同日重查**覆盖**
  旧值（越靠近收盘的估值越准，留着早盘那版只会让复盘多出一个「早盘必然高估」的系统性
  偏差 —— 那是采样时机的问题，不是估算算错了）。**这份流水同时就是本页首屏的缓存**：
  `/api/fund-estimate/last` 回读它，让页面打开就有上次的结果 —— 同一批数据喂两张表，
  写它不是白写。
- **拿到有效涨跌幅的行才记**：空行记进去只会变成永远闭合不了的 pending。反过来，
  **某天估算失败、但接口带回了真实净值，那条净值照样存** —— 它是别的日期算实际涨跌幅
  要用的 `prev`。
- **删关注不抹复盘**：`fund_watchlist` 和两条流水是三张表，取消关注只是不再查它，
  已经攒下的历史照算。

> **研究性工具**：盘中估值由公开数据估算得出，**不代表基金真实净值** —— 持仓数据滞后于
> 基金经理实际调仓，估算口径与延迟以数据源为准。上面那张 T+1 复盘表同样只是**历史估算与
> 已公布净值的差异**，是对过去的对账、不是对未来的预期。两者都仅用于数据可视化研究，
> **不提供任何买卖信号，不构成投资建议**；未通过校验的字段一律留空，不做补齐。

## 点击代码打开同花顺

四池（涨停 / 炸板 / 跌停 / 强势）、主力建仓候选、总览 Top5、关注列表里的**股票代码是可点的**，
点一下在你本机的同花顺客户端里打开该股详情。

- **原理**：同花顺注册了 `hexin://` 协议（注册表命令就是 `"hexin.exe" %1`），所以做法是最朴素的
  `<a href="hexin://…">` —— 浏览器交给系统、系统交给同花顺，**前端不调后端、不创建任何进程**，
  也就不需要「开进程」这种危险接口。
- 首次点击浏览器会问「要打开 同花顺 吗？」，勾**始终允许**后不再提示。
- **深链接模板**（`hexin://quote?code={code}`）是按最可能的写法先放的：跳哪只股票的 URL 没有
  公开文档，二进制里也只有 CEF 的 scheme 白名单、没有格式串。试出来换一行即可（vite 热更），
  控制台 `localStorage.setItem('ths.template', …)` 也能临时试，详见 `frontend/README.md`。

「清单详情」（涨跌停全景页），从清单里点一行才进个股详情 `/stock/{code}`：

|---|---|---|
| 总览统计卡（涨停 / 炸板 / 跌停 / 强势股） | 整张卡片 | `/limit?tab=…` 对应池清单 |
| 总览「最高连板」卡 | 整张卡片 | 该龙头个股详情 |
| 总览「已关注」卡 | 整张卡片 | 关注股票页 |
| 总览连板梯队金字塔 | 柱子 | `/limit?tab=zt&boards={N}`（该板级的个股清单） |
| 四池清单 / 总览 Top5 | 整行 | `/stock/{code}` 个股详情 |

清单页（`/limit`）就是**卡片与柱子共用的那个详情页**：只认 URL 参数 ——
`?tab=zt\|zb\|dt\|strong` 预选池，`?boards=N` 过滤连板数，筛选条上带「清除筛选」。
换池 / 换筛选都只改参数，因此总览和清单之间来回跳不会丢状态。

个股详情页（`StockDetail`）的内容：

- **走势** —— 近 90 个交易日 K 线 + MA5 / MA20 + 成交量，底部 dataZoom 可缩放；
  顶部 5 张卡：最新收盘、当日涨跌幅、近 90 日累计、区间最高 / 最低、最新成交额与换手。
- **主力净流入** —— 近 10 个交易日柱状图（红入绿出）+ 右侧逐日明细表，卡片头部给区间合计。
- **档案** —— 命中了哪个池（几板 / 开板几次 / 跌停 / 强势）、主力建仓打分
  （综合分、排名、覆盖率、入选拆解）、关注状态（建仓日、当时的排名与分数）。
- 顶部可直接**关注 / 取消关注**，写入的快照与主力建仓页点星标的口径完全一致。

数据口径：K 线走 `GET /api/stock/{code}/daily`（**后端缓存 30 分钟**，逐只点开也不会把
数据源打爆），资金流与档案全部只读库。各块**独立兜错**，某个源挂了只降级那一格
（比如东财日线被封时走势图给提示，档案和资金流照常显示），页面不会白屏。

> **研究性工具**：详情页只呈现已发生的行情与当时的打分，不给任何买卖信号，不构成投资建议。

## 打分模型（M4）

六个维度先各自在候选池内做**百分位归一化**（0-100），再按 `backend/config/scorer.yaml`
的权重加权求和。量纲不同的指标（元 / 百分比 / 无量纲）因此可以直接相加。
指标定义的权威版本是 `docs/01` §8.3：

| # | 维度 | 权重 | 指标 |
|---|---|---|---|
| 1 | 主力资金持续流入 | 30 | 近 5 日净流入/流通市值 **且** ≥3 日为正（两子证据相乘） |
| 2 | 放量但不涨 | 20 | 近 5 日均量/20 日均量 ∈ [1.5,4] **且** 近 5 日涨幅 ∈ [0%,12%] |
| 3 | 大单净额占比 | 15 | 近 5 日 (超大单+大单净流入)/成交额 均值 |
| 4 | 股价位置低 | 15 | 现价在近 250 日最高-最低区间的分位（越低越好） |
| 5 | 换手适中 | 10 | 当日换手率 ∈ [3%, 12%] |
| 6 | 筹码收敛 | 10 | 近 10 日均振幅 / 前 20 日均振幅 < 0.8 |

硬区间都实现成**甜区函数**（区间内 1 分、区间外线性衰减）：硬阈值在百分位排序下
会让区间边缘的两只股票产生断崖差，而它们其实只差一点。

**两个必须知道的运行时特性**：

- **逐日序列靠自我积累**。维度 1 和 3 都要跨交易日的序列，每天盘后把当日净额
  快照写进 `stock_net_inflow`。**冷启动只有当天一天**，连续性与 5 日均值算不出来，
  结果里会标注降级并按剩余维度重归一化权重。
- **维度 3 只有东负能给**（大单分解）。本网络东财 `push2` 被挡，实测该维度长期
  覆盖率 0%，会整维弃用、权重从 100 降到 85；同花顺/腾讯回退路径不含大单分解。

### 上榜矩阵（跨日回看）

「主力建仓候选」页顶部有两个 Tab：**最新榜单**（原来的单日视图，配日期下拉回看）
与 **上榜矩阵**。

矩阵就是一张 Excel —— **纵向是股票、横向是交易日**，格子写当天名次，
日期列随统计天数自然变多：

```
                09/24  09/28  09/29  09/30  10/08  10/09   上榜次数
  002467 二六三    ·     #25    ·      #8     #3     #12        4
  002487 大金重工  #6    #22    ·      ·      #6     ·          3
```

**三种格子必须分开读**，混了会得出相反结论：

| 格子 | 含义 |
|---|---|
| `#8` | 当天进了 Top30，数字是名次（悬停显示综合分） |
| 灰底 | **这天压根没跑任务** —— 不是"跑过但没上榜" |
| 空白 | 跑了，但这只没进 Top30 |

漏跑的交易日**照样占一列**，表头标「未跑」。列取自交易日历而不是「有数据的日期」；
日历走 `calendar.cached_trade_dates()` —— **只读本地文件、过期也不联网**，
不会为了列几列日期去触发一次会被内网安全设备拦截记录的外网请求。

默认按**上榜次数降序**，其次最近上榜日、再次最好名次；页内可切 30 / 90 / 365
个交易日的范围。

**「补跑」按钮长在漏跑那一列的表头上** —— 缺哪天，按钮就出现在哪天的日期旁边。
点它走 `POST /api/main-force/refresh?date=<那天>`，与榜单页「重新打分」是同一个接口、
只是多带一个日期，不重复造轮子。跑一轮约 12-15 分钟，**内网环境下外网行情接口会被
安全设备拦截并记录**，悬停提示里写了。跑完轮询自动刷新矩阵，该列随即由灰底转为正常列；
补跑期间只有被点的那天显示 loading，其余日期按钮进入禁用态。

> ⚠ **补跑过去的日期不完全等于当日实跑**。快照 `market_snapshot()` 抓的是**当前**行情，
> 而补跑的目标日已经过去。已修的部分：**维度 5「换手适中」(权重 10)** 与输出行的
> `price / pct_chg / turnover / amount` 现在优先走 `_asof()` —— 取日线里**恰好等于
> `trade_date`** 那一行；那天缺行（停牌 / 日线还没更新到当天）才退回快照，
> 绝不拿前几天的值冒充当天。
>
> 仍然取自当前快照的部分：**粗筛**的停牌 / ST / 成交额过滤、**候选池预选**
> （决定哪 300 只去拉日线 —— 预选跑在取日线之前，拿不到 as-of 换手）、
> 以及 `float_mv`。所以补跑历史日的候选集与当日实跑仍可能有出入。
> 补跑**当天**不受影响 —— 快照本来就是当天的。详见 `docs/04-backlog.md` §4 挂起项二。

> 实现是**读时聚合**：每次解开已有 `main_force` 快照的 `rows`（Top30）拼表，
> 不动打分主链路。90 天口径实测 **0.04s**。历史拉长后应升级成紧凑表
> `mf_history(code, name, trade_date, rank, score)`（打分落库时顺手写一行），
> 已记在 `docs/04-backlog.md`。

## 历史补录

左侧菜单「**历史补录**」（`/replenish`，`app/pipeline/replenish.py`）：把主力建仓候选页缺的
历史数据补回来 —— 上榜矩阵、前5跟踪的历史深度 = 打分跑过的天数，冷启动只有几天，
这里就是把 2026-01-01 起的数据补齐。四个按钮 = 四条流水线，**点了才会联网**
（服务启动、页面刷新、任何定时器都不碰），全部**断点续跑**（判据：bars 查区间覆盖、
inflow 查 kv 完成清单、pools/score 查库缺哪天补哪天）：

| 按钮 | 补什么 | 量级 | 说明 |
|---|---|---|---|
| ① 日线全历史 | `daily_bar` 不复权 OHLCV + 复权因子 | ~1 万次请求，5-8h | 走统一任务入口 `run_task("historical_backfill")` 分批跑，单批失败率过高自动停 |
| ② 资金流全历史 | `stock_net_inflow` 逐日主力净流入/大单净额 | ~5400 次请求，3-5h | 东财 `stock_fflow_daykline` 一只一次回全历史；**只补缺失格**，已有当日快照不覆盖 |
| ③ 池子补采 | `pool_zt/zb/dt/strong` 近 30 天 | 少量，1h 内 | 东财只留 30 个自然日，过期**永久不可补**（收盘当场采的），页面如实列哪些日期补不了 |
| ④ 历史打分补跑 | `main_force` 逐日打分 | 12-15min/天 | 只覆盖池子拿得到的日期；更早的日期跳过并写明原因（「历史模式打分」支持后同按钮全覆盖） |

建议顺序 ①→②→③→④（④ 依赖 ① 的日线、③ 的池子）。同 job 不并发（409），
不同 job 可并行（熔断按域分桶，日线与资金流不同域）。**在家庭/服务器网络跑** ——
内网下这些请求会被安全设备拦截并记录。

## 数据管理（占用与清理）

左侧菜单最后的「**数据管理**」（`/data`）。回答三个问题：数据占了多少、哪些是垃圾、
删了会不会出事。

**数据存在哪** —— 全在一个 SQLite 文件 `backend/data/market.db`（4 张表）：
`snapshot`（所有行情数据，`(dataset, trade_date)` 主键、`payload` 是整块 JSON）、
`job_run`（任务日志）、`watchlist`、`kv`（配置，**含飞书 App Secret**）。
外加同目录的 `trade_calendar.json`。没有第二份数据目录。实测 **3.73 MB**：

| dataset | 内容 | 实测 | 说明 |
|---|---|---|---|
| `stock_net_inflow` | 逐日主力净流入 | 1.63 MB / 10 天 | 每天约 4737 只 × 4 字段，**增长最快**（约 110 MB/年） |
| `main_force` | 主力建仓打分 | 1.44 MB / 5 天 | 每天约 290 KB，其中 `all_rows` 占 **90%** |
| `pool_*` | 涨停 / 炸板 / 跌停 / 强势 | 0.46 MB / 各 5 天 | 逐日累积 |
| `sector_flow_*` | 行业 / 概念资金流 | 0.11 MB | **只存 `latest` 一行，天然不累积** |

**8 个 dataset 一个孤儿都没有**（全都反查过读取方），所以没有「没人用的数据」可删。
唯一的大头是 `main_force.all_rows`（约 265 KB/天），但它**被三处在读** ——
`GET /api/main-force?all=true`、飞书摘要、关注股的候选池判断，**不能删**；
真要瘦身只能拆行或压缩，已记在 `docs/04-backlog.md`。

### 三道安全设计

1. **默认 `dry_run`** —— 不确认绝不写库。前端「确认删除」在拿到预览结果前是禁用的。
2. **真删要两道门** —— `dry_run=false` **且** `confirm="DELETE"`，少一个返回 400。
3. **硬下限**（`db.DATASET_FLOOR`，含义是「**删完至少还要剩几天**」）：

| dataset | 底线 | 为什么 |
|---|---|---|
| `stock_net_inflow` | **5 天** | 打分维度 1（近 5 日净流入/流通市值）与维度 3 要跨日序列，不足 5 天该子信号变 NaN、模型 degraded |
| `main_force`、`pool_*` | **1 天** | 少于 1 天该 dataset 空了，榜单 / 矩阵 / 日期下拉直接变空白 |
| `sector_flow_*` | **不可删** | 只有 `latest` 一行，删掉板块页就空了 |

> ⚠ 代码里那些 `limit=30` / `limit=60`（`list_dates` 的调用参数）**不是**硬下限 ——
> 它们只是日期下拉的显示上限，库里只有 5 天时照常显示 5 天、不会崩。
> 早期实现把 30 / 60 当底线，结果实测「库里 5 天，想删哪天都删不掉」，把用户锁死了。
> 所以策略值（`settings.retention_*`）和底线（`DATASET_FLOOR`）是分开的两套：
> **前者可调，后者不可越。**

`kv`（凭据）与 `watchlist`（用户数据）不在任何清理范围内；`/api/data/usage`
对 `kv` **只回键名**，值接口不回传。

### 为什么删完文件不缩小

该库 `auto_vacuum=0` —— 删除只是打标记，文件不会变小，必须显式 `VACUUM`
才真回收（实测 3.7 MB 的库回收 **1.24 MB**）。页面上「可回收空间」就是
`freelist_pages × page_size`。

### 日志轮转

`run/*.log` 是启动器把子进程 stdout 重定向写进去的，后端自己不持有句柄：

- **轮转在下次启动时做**（`scripts/start_all.py` 的 `rotate_log`，阈值
  `settings.log_max_bytes` = 20 MB）：运行中的文件被写入方占用、Windows 上
  改不了名，只能在启动前把超阈值的挪成 `.1`（只留一份，旧的覆盖）；
- 运行中只能**原地清空**（`truncate(0)`，写入方的句柄与偏移都不受影响），
  日志名走白名单 —— 传路径进来**预览阶段就 422**。

### 保留策略

`backend/app/config.py` 里三个值（页面上直接展示当前配置）：

| 配置 | 默认 | 对应 |
|---|---|---|
| `retention_main_force_days` | 365 | 矩阵 `days` 的上限 |
| `retention_inflow_days` | 60 | 打分只要 5 天（`inflow_window_days`），60 是余量 |
| `retention_pool_days` | 60 | 日期下拉 `list_dates()` 默认 limit=30 |

「按保留策略清理」= 一次把每个数据集最老的那些天清掉，**实际保留取
`max(配置值, 硬下限)`**，`sector_flow_*` 不进计划。两点要注意：

- 只按**库内已有日期**倒序算，不推交易日历 —— 推日历会让旧数据随时间自动
  「过期」，长期没跑的库会被误清；
- **预览删什么，真删就删什么**：要删的日期清单在预览时算好存住，真跑直接用，
  不重算（否则两次读之间落了新数据，实际删的会和你看到的不一致）。

目前**没有自动定时清理** —— 保留策略要手动点（页面上预览 + 二次确认）。
`job_run` 的「超出保留 N 行」分支（`unfinished_only=false`）也只在接口层支持，
页面只暴露了「清未收尾残留」。

## 四个必须知道的坑

### 1. 网络：IPv6 坏节点 + 限流

`push2.eastmoney.com` 的 IPv6 节点（`240e:e1:...`）TCP 能建连但 HTTP 层被 RST，
Python 只在 TCP 建连失败时才切换地址，因此**无法自动降级到 IPv4**，请求直接失败。

`app/netfix.py` 做四件事：**IPv4 优先排序**（保留 IPv6 回退）、**按域名分级限速 + 随机抖动**、
**默认超时兜底**、**总时长闸门**（见坑 3）。

高频请求会触发东财 IP 限流（`RemoteDisconnected`），同花顺、新浪不受影响。
限速是按域分桶的 —— 之前用全局 1s，把同花顺百页分页接口从 0.1s 拖到 105s；
每次请求在最小间隔之上**再随机多等一段**（固定匀速是最像机器的节奏）：

| 域 | 最小间隔 | 随机抖动 | 实际间隔 |
|---|---|---|---|
| 普通源（同花顺 / 新浪 / 腾讯 …） | 0.35s | 0 ~ 0.5s | 0.35 ~ 0.85s |
| 东财 push2 / push2his（实测会封） | 1.5s | 0 ~ 2s | 1.5 ~ 3.5s |

对应配置（`backend/.env` 可覆盖，前缀 `STOCK_`）：`REQUEST_INTERVAL`、
`REQUEST_SENSITIVE_INTERVAL`、`REQUEST_JITTER`、`REQUEST_SENSITIVE_JITTER`。
等某个域名时**睡在锁外**，不会把其它域名的线程一起按住。

详见 `docs/02-数据源与网络排查.md`。

### 2. 数据：`date` 参数非交易日会静默返回错误数据

`stock_zt_pool_em(date=...)` 在传入非交易日（如周末、节假日）时**不报错**，
而是返回最近一个交易日的数据。若不做交易日校验，会把 A 日数据当 B 日用。

**所有取数必须先过 `fetchers/calendar.py` 校验日期。**

实测：2026-09-25 为中秋节假期，最近交易日是 2026-09-24。

### 3. 网络：akshare 不传 `timeout`，不设兜底会永久挂起

akshare 绝大多数接口调 `requests.get()` 时**不传 `timeout=`**。一旦对端建连后
不回包，Python 会一直 `recv()` 等下去：**没有异常、没有超时、没有日志**，
定时任务就永久卡死。

症状很典型：进程 CPU 恒为 0，只有一条 `ESTABLISHED` 连接，日志几分钟不更新。

`netfix._throttled_request` 在 `Session.request` 层统一补 `timeout=(5.05, 30)`
（调用方显式传了就不覆盖）。此外每个数据源都带**连续失败熔断**，成功即清零计数：
对端偶尔超时会重试，连续挂了就立刻停手，不让 300 次逐只请求空耗几小时。

**光补 `timeout` 还不够 —— `read` 只管「单次 recv」。** 服务端只要每次 `recv`
都在 read 秒内回哪怕 1 字节，超时就永不触发，`Content-Length` 没读满就一直等
下去。实测：本地滴流服务端 0.3s/字节，客户端 `timeout=(2,2)` 下请求 **HUNG >6s**。

所以 `netfix` 再加一道**总时长闸门**：每次请求挂一个绝对截止时刻（默认 120s），
`recv` / `recv_into` 前把套接字超时收紧到剩余预算，耗尽直接抛 `socket.timeout`。
收紧动作落在 `settimeout` 上而不是改调用方式，因为 HTTPS 走 C 层 `SSL_read`
**根本不经过 Python 的 `recv`**，只有套接字上的 `SO_RCVTIMEO` 穿得透。
闸门只在有活动截止时刻且套接字为阻塞模式时介入，同进程的 uvicorn/asyncio
（`gettimeout()==0`、事件循环线程读不到线程局部值）完全不受影响。

### 4. 工具：uvicorn `--reload` 遇到语法错误会静默卡死

`--reload` 期间如果改动引入了语法错误，会出现：reloader 打印一行
`WatchFiles detected changes ... Reloading...`，然后**worker 既不重启也不退出**，
旧代码继续服务；你把语法错误修好之后，它也**不会再触发 reload**。

结果就是接口悄悄 404 / 代码悄悄是旧的，日志里没有任何报错。

**发现方式**：新增的路由 404，但日志里没有 traceback。
**解决**：直接重启进程，别指望 reload 自愈。
